# 诊断与归因

> 出问题的第一件事不是改代码，是回答「**该谁背**」：内核、某个插件，还是装配。
> 猜错方向的代价是改错地方、越改越乱，最后把「装配问题」写成「内核限制」。

## 1. 四个命令

| 工具 | 回答什么 | 命令 |
| --- | --- | --- |
| 装配诊断 | **有什么**：插件、节点、面板、设置、语言包、原生族、缓存位置 | `-- --fx-diagnose` |
| 归因诊断 | **谁的错**：每条问题判给内核 / 插件 / 装配 | `--fx-diagnose --fx-run=diag.blame` |
| 工程诊断 | **这个工程**谁的错：节点类型 / 算子 / 端口 / 参数 / 求值告警，并给逐节点耗时 | `--fx-diagnose --fx-run=diag.project --fx-arg=<path.fxproj>` |
| 原生实况 | **库在不在**：加载了哪些库、绑定了几个类、哪些算子不许跨线程 | `--fx-diagnose --fx-run=diag.abi` |
| 依赖索引 | **停用它掉什么**：谁的键被谁注入、算子由谁实现、哪些供给没人用 | `--fx-diagnose --fx-run=diag.deps [--fx-arg=<插件 id>]` |
| 缓存归因 | **谁在重建、值不值**：桶重建次数、来源、失效档位 | `--fx-diagnose --fx-run=diag.cache` |
| IR 报告 | **图编译成什么**：拓扑序、类型、常量折叠、Live/Dead、帧段 | `--fx-diagnose --fx-run=diag.compile` |

```bash
GODOT="D:/SteamLibrary/steamapps/common/Godot Engine/godot.windows.opt.tools.64.exe"
"$GODOT" --headless --path . -- --fx-diagnose --fx-run=diag.blame
"$GODOT" --headless --path . -- --fx-diagnose --fx-run=diag.cache --fx-arg=reset
```

前两个查静态结构（谁引用谁、谁的贡献缺了），后两个查运行时与编译形态。
`diag.blame` / `diag.cache` 由 `editor.diagnostics` 贡献，`diag.compile` 由 `core.compile` 贡献——
**三个都是插件，停用即消失**，基座里不留钩子。

## 2. 输出怎么读

```
== 归因诊断 ==
内核契约 0.1.8 · 应用 0.0.20-alpha · 工程格式 0.1 · 插件 48
没有发现可归因的问题。
── 汇总 ──
错误 0 · 警告 0 · 信息 0 ｜ 需要动手：内核 0 / 插件 0 / 装配 0
```

- 标记：`✗` 错误、`!` 警告、`·` 信息（信息不计入"需要动手"）。
- 归属：`[内核]` / `[插件:<id>]` / `[装配]`。
- `@` 后面是证据位置（文件或节点定义），可以直接跳过去。

**「需要动手」那一行是唯一行动依据。** 内核数不为 0 时先修内核：
基座编译不过时，什么插件都装不上，此时"插件问题"也不可信。

### 2.1 工程诊断怎么读（`diag.project`）

`diag.blame` 看的是**装出来的环境**（谁引用谁、谁的贡献缺了），它不认识任何一个工程文件。
「这个工程打开后某个节点不生效」那类问题要靠 `diag.project`：它把一个 `.fxproj`
**只读地**解析出来（不打开、不解素材、不动工作台），然后逐节点核对：

| 判据 | 归属 | 说明 |
| --- | --- | --- |
| 节点类型在本机找不到定义 | 插件（未安装） | 装回提供该类型的插件即可，不是内核 |
| 有定义但算子没实现 | 定义方插件 | 它承诺了一个没人注册的 op；若对方的原生库有加载错误，改判原生包（见 §2.3） |
| 跨插件借算子但**已声明** `inject` | 信息（不算动手） | 按「定义方→提供方」合成一条：28 个节点不会刷 28 行 |
| 连线指向不存在的节点 | 装配 | 工程文件残缺或被手工改过 |
| 连线指向不存在的端口 | 端口所在节点的定义方 | 端口改名了、工程没迁移 → 那条线永远不生效 |
| 节点里留着定义中没有的参数 | 定义方插件 | 改名没做迁移，用户改它不会有任何反应 |
| 参数默认值落在 min/max 之外 | 定义方插件 | 拖出来就是非法值，滑块一动就跳边界 |
| 求值告警 | 按文本里的节点 id 反查 | 没有 id 的告警说明上报点缺上下文 |
| 工程随包带了本机没有的插件 | 装配 | 缺插件时一切「节点找不到」都是它的后果 |

最后一段是**逐节点耗时**（`ctx.timing_totals`）：

```
── 逐节点耗时（本帧，只报数不判罪）──
   1. toon_view            32.7 ms  → fx.stylize
   ...
  整帧 245.1 ms
```

它只回答「时间花在谁身上」，**不回答「谁写错了」**——慢可能是因为画布大、
可能是这条链本来就该慢。要判性能责任请用 Profiler 与 `docs/性能口径.md` 的口径。

```
== 工程诊断 ==
工程 res://examples/demo/示范工程.fxproj · 103 节点 · 81 边 · 画布 192×108 · 2.00s@30
涉及插件（18）：anim.curves, …, glow, godot.export
节点类型 77 种 · 定义命中 103/103 · 算子命中 103/103
没有发现可归因的问题。
── 汇总 ──
错误 0 · 警告 0 · 信息 0 ｜ 需要动手：内核 0 / 插件 0 / 装配 0
结论：内核 0 / 插件 0 / 装配 0 —— 这个工程在本机是干净的。
```

### 2.1.1 另外两条：原生实况、依赖索引

| 命令 | 回答什么 | 一次典型输出里的关键行 |
| --- | --- | --- |
| `diag.abi` | **原生库在不在**：加载了哪些库、绑定几个类、哪些算子不许跨线程 | `ABI 版本 1 · 已加载库 2 · 绑定类实例 5 · 算子 111（原生 29）` |
| `diag.deps [--fx-arg=<id>]` | **停用它掉什么**：服务依赖、算子依赖、没人 inject 的供给键 | `fx.native-kit 6 个算子 ← fx.keying` |

`diag.abi` 刻意**不引用任何具体原生类**：它只用内核的 `FxNative`（库清单 / 绑定数 /
非线程安全标记 / ABI 版本）和各插件自己的 `status_fragments()` 诊断行。
这样某个原生插件停用或改名，诊断自己不会解析失败。

`diag.deps` 的三条边全部从清单与账本推出来（`provide` × `inject`、节点定义方 × 算子提供方），
不读代码。带 `--fx-arg=<插件 id>` 时只列那个插件的消费者 —— 这是"我准备停用它了，
会掉什么"最直接的答案。

`diag.compile` 也支持 `--fx-arg=<fxproj>`：编译磁盘上的工程而不是当前文档。
工程读取走能力键 `project.read`（由 `editor.diagnostics` 提供）；
提供方缺席时**明确报错**，不偷偷退回当前文档 —— 那会让人以为跑的是那个工程。

### 2.1.2 缓存事件的无头回放

```bash
"$GODOT" --headless --path . --script res://tests/tool_cache_replay.gd \
      --fx-replay=res://tests/replay/sample.json
```

动作表（`open` / `param` / `time` / `canvas` / `settle`）逐条执行，打印每步新增的事件：
闸门判定（`layout_only` / `identity_same` / `downstream` / `content`）、换桶（含 `silent` 标记）、
失效档位。用来回答"这次重建是谁引起的"。
**为什么不是 `diag.cache --fx-arg=script:<json>`**：命令是同步 Callable，跨帧回放需要帧循环。

### 2.2 一条容易误读的信息：跨插件借算子

`fx.*` 那五个节点插件的算子全在 `fx.native-kit`（C++）里，所以结构扫描会看到
「节点定义在这里、算子在别处」。**这不是缺陷**：它们的 `plugin.json` 里
`inject: ["plugin.fx.native-kit"]` 登记了这条依赖。判定依据就是这句声明 ——
不看代码怎么写，看清单怎么声明。

```
· [插件:fx.keying] fx.keying 的 6 个节点，算子由 fx.native-kit 提供（已在 inject 声明）
    → 跨插件依赖已登记：停用 fx.native-kit 时这些节点会跟着不可用，这是设计好的边界。
```

没声明的跨插件借算子才是警告：那种情况下停用提供方，节点会静默失效。

### 2.3 原生库没加载时，别再怪节点定义

28 个算子的实现都在 `fx.native-kit` 的 DLL 里。库没加载时，如果逐条报"某节点没实现"，
会得到 28 条错误、且全部指错人 —— 真因只有一个：那份库没起来。

判据三条同时成立才改判（少一条都可能把"op 名写错"误判成"库坏了"）：

1. 节点定义方的 `inject` 里声明了某插件的 `provide` 键；
2. 那个插件的 `plugin.json` 里有 `native` 字段（它是原生包）；
3. 那个插件的账本里有 `kind=error`。

实测（把 DLL 改名后跑 `diag.blame`）：

```
✗ [插件:fx.native-kit] 原生库加载失败：… res://plugins/fx.native-kit/fx_native_kit.gdextension
✗ [插件:fx.native-kit] fx.keying 的 6 个算子没有绑定：fx.native-kit 的原生库没有加载
✗ [插件:fx.native-kit] fx.tone 的 5 个算子没有绑定：fx.native-kit 的原生库没有加载
── 汇总 ──
错误 6 · 警告 0 · 信息 0 ｜ 需要动手：内核 0 / 插件 6 / 装配 0
```

6 条、全部指向 `fx.native-kit`，并且提示直接给重编命令。
**没有一条怪到 `fx.keying` 的节点定义上** —— 这才是"分清谁的错"。

## 3. 归属从哪来（本版最大的改动）

上一版靠**措辞**判断归属：错误文本里没有插件 id → 判内核。于是
「`plugins/pixels.native` 缺 `plugin.json`」这条被算成内核问题——而它既不是内核，
也不是某个插件，是**装配**（扫描步骤发现自己扫到一个不像插件的目录）。

现在归属由**声明**给出：

```gdscript
FxBoot.error(where, message, scope)
#   scope = ""            未声明 → 回落到文本推断（旧规则）
#         = "kernel"      基座自己的启动步骤
#         = "assembly"    扫目录 / 读清单 / 依赖与供给键协调
#         = "plugin:<id>" 某个插件
```

判定顺序：

1. `scope == "assembly"` → **装配**，提示"先看目录结构与 plugin.json，别急着改内核"；
2. `scope` 以 `plugin:` 开头 → **插件**，owner 直接给出；
3. `scope == "kernel"` → **内核**；
4. 没有 `scope` → 文本里能认出插件目录就归插件（标注"文本推断"），否则归内核。

## 4. 判据表（工具就是按这些判的）

| 现象 | 判给谁 | 为什么 |
| --- | --- | --- |
| 基座源码出现插件 `class_name` | **内核** | 该插件一停用，`scripts/graph` 连编译都过不了 |
| 账本里 `kind=error` 的项 | 账本 `owner` | 贡献点自带归属，不用猜 |
| 节点定义了但 `op` 查不到 | 节点定义所属插件 | 它承诺了一个没人实现的算子 |
| 节点定义与算子分属两个插件 | **定义方** | 跨插件依赖没在清单里声明，停用对方就静默失效 |
| 缺供给键 / 依赖环 / 未激活 | 声明方插件 | `dependency_report()` 的事实 |
| 启动错误带 `scope=assembly` | **装配** | 扫描 / 清单 / 协调阶段的问题 |
| 启动错误无 `scope` 且文本无插件痕迹 | **内核**（临时归因） | 只能按文本猜，会误判；见到就把 `scope` 补上 |
| 绑定型参数（`binds`）在文档里存了非 0 | **节点定义所属插件** | 它让同一份事实有了两个来源，输出帧尺寸与帧缓存布局对不上，每帧都被尺寸闸门丢掉 |

最后一条是本版新增，也是最难从别处发现的一类：「画面卡死、不报错、日志干净」。
它只存在于**当前文档**里，注册表扫描看不见 —— 所以 `diag.blame` 现在会读一遍
打开着的文档，命中就报 `插件 error`，并指出把值清成 0、尺寸改到文档画布上。

**刻意不猜的两件事**：不算"性能慢是谁的错"（看 Profiler 与逐节点计时），
不算"画面不对是谁的错"（看算子级对照测试）。

## 5. 三个常见误判

### 5.1 「插件停用后界面报错」不一定是插件的错

如果报错来自基座对插件类名的引用，责任在内核：它没为该能力留契约，
只是"碰巧"在插件在的时候能跑。

### 5.2 「算子缺失」经常是节点定义写错了名字

`op` 是纯字符串，写错不会在加载期报错，只会在求值时 `push_error`。
归因诊断会在启动后立刻扫一遍全部节点定义，把这类错误提前到"装完就知道"。

### 5.3 「多个插件实现同一个 op」不是冲突

后登记的覆盖先登记的（`FxRegistry.ops[key] = value`），这是**有意设计**：
`render.gpu` 覆盖 `image.blur` 就是这个机制。所以工具只在
「节点所属插件自己**一个**实现都没有」时才报跨插件依赖。

## 6. 缓存归因怎么看

```
采样 18 条（桶重建 3 · 空转 1 · 失效请求 6 · 变更通知 8）
  t=1.20s invalidate tier=derived source=quality.operator ready=12
  t=1.24s bucket 2273364494→1333485966 帧 60→6 变化：节点~blur
```

- `tier` 是失效档位（`content` / `derived` / `display`）。**档位报高**（该 `derived`
  却记 `content`）会让整桶白算，是最常见的性能债。
- `变化：` 后面是分段哈希的差异来源（`nodes` / `edges` / `meta`）。只有 `meta` 变了
  却要重建，通常意味着有人把视图态混进了内容键。
- `--fx-arg=reset` 先清空再统计。**无头下没有交互，采样必然是 0**——
  这是当前最大的工具缺口，见 §7。

### 6.0 标尺四色与「画面为什么是糊的」

标尺上的色块现在有四档，分属**两个不同的问题**，别混着读：

| 颜色 | 值 | 回答的问题 | 谁能改它 |
| --- | --- | --- | --- |
| 红 | 0 | 这一格算过吗 | 求值 |
| 黄 | 1 | 只有垫图（草稿 / 播放档）吗 | 求值（低质量档） |
| 绿 | 2 | 精确帧在缓存里吗 | 求值 + 归档 |
| **橘** | 3 | **现在有线程正在算这一格吗** | 调度（`set_rendering`） |

橘色不是缓存状态：它由预渲染/急件的在飞登记表每帧整批覆盖，任务结束就消失。
黄格有两个来源：**草稿趟**（整段按 1/8 画布铺一遍，很快）与播放档急件。
状态栏会写清「草稿 f12 1/8」—— 屏幕糊的时候，用户至少知道它在干什么、还差多少。
`cache.state()` 永远不返回 3 —— 播放的挂起条件按它判断「这一格有没有图」，
让「正在算」混进去会让播放以为有图可贴。

`diag.cache` 的「两条预览管线」段落里还有一行 `动态质量`：它报告草稿阶梯、
最近一次提交的档位，以及**最近一次草稿有没有真的上屏**。没有「已上屏」标记，
就说明草稿线程在算但结果被身份校验丢掉了（换了文档 / 换了播放世代），
那不是「草稿不生效」，是「它算的那一帧已经不是当前帧了」。

`publish-drop` 事件（`diag.cache` 里会出现在重建事件流里）表示**一张图被上屏闸门拦下**：

```
publish-drop why=canvas got=(128, 128) want=(192, 108) frame=0
```

它最常见的成因是「改画布 / 改参数的那一刻有在途结果」。**偶发一两条是正常的**；
若持续刷屏，说明有人在反复请求一个永远不会满足的尺寸（通常是发布路径绕过了
`_canvas_size()`）。

### 6.1 单节点追踪：`FX_TRACE_NODE=<节点 id>`

「改了参数没反应」不必再靠猜。带上这个环境变量跑（开窗或无头都行）：

```bash
FX_TRACE_NODE=fg_bloom godot --path . --script res://tests/runtime_smoke.gd
```

执行器会对该节点打印每一帧的判定：

```
[node] fg_bloom 未命中 → 重算 sig=201156620473 cached=true static_cacheable=true
[node] fg_bloom 命中缓存 sig=201156620473 out_img=<Image#...>
```

- `sig` 不变 = 内容签名没跟上参数（那才是 bug）；
- `cached=true` 而 `sig` 变了却仍命中 = 命中判定写错了；
- 完全不出现 = 这个节点本帧没被求值（不在输出链上 / 被剪枝）。

## 7. 这个工具还不够好的地方

| 缺口 | 现状 | 打算 |
| --- | --- | --- |
| `diag.compile` 只能看启动示例文档 | 固定 6 个节点，看不到真正的工程 | 加 `--fx-arg=<path.fxproj>` |
| `diag.cache` 在无头下永远 0 条 | 只能开窗用，验收无法复算 | 加声明式操作回放 `--fx-arg=script:<json>` |
| 原生扩展没有专门检查 | 只能靠跑整套逐字节测试 | 新增 `diag.abi`：逐族在场、绑定数、ABI 版本 |
| 「删任一插件仍能启动」是手工试 | 没进闸门 | 新增 `diag.deps`：贡献 → 消费者反向索引 |
