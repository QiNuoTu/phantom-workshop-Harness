# 性能口径

> 性能数字只有**口径**才有意义。这份文档规定口径，记录实测，并明确写出
> 「哪些看起来像提速、其实不是」——上一版把结构剪枝的上界写成了提速，是典型的自欺。

## 1. 唯一口径

| 项 | 规定 |
| --- | --- |
| 工程 | `examples/demo/示范工程.fxproj`（103 节点，192×108，60 帧，3 条 `ease` 轨道） |
| 模式 | 无头（`--headless`）；需要开窗的数字**单独标注**，不与无头混比 |
| 预热 | 至少跑一帧再计时（首次含 ~0.85s shader 编译） |
| 加速开关 | 对照时用 `FX_NATIVE=0` / `FX_GPU=0`，其余条件不动 |
| 统计量 | 单帧累计耗时（不是"最后一次"）；多次取中位 |

开窗比无头稳定多 **约 40 ms**（显示服务器抢主线程）。这两个数字**不能放同一张表**。

## 2. 仪器

| 脚本 | 回答什么 |
| --- | --- |
| `tests/_profile_frame.gd` | 单帧成本归属：逐算子累计 + 调用次数 + 框架开销 |
| `tests/_profile_overhead.gd` | 框架开销逐项（端口表 / 文档哈希 / 预览捕获） |
| `tests/_bench_res_scale.gd` | 分辨率档的加速比（192² / 512²） |
| `tests/_bench_native_ops.gd` | 单算子原生 vs GDScript 的倍数 |
| `tests/_bench_parallel.gd` | GDScript 行内并行的效率天花板 |

**为什么不用 `ctx.timings`**：它只留每个节点的**最后一次**耗时，循环体里被重复求值的
节点会被严重低估（`flow.for` × N）。必须用累加值 `timing_totals` + `op_calls`。

## 3. 当前实测（无头）

**最新一次（第六轮，2026-11-17）**：整帧 **69.04 ms** · steps=104 · 求值节点 85 ·
算子累计 44.12 ms（63.9%，97 次调用，平均 0.45 ms/次）· 框架/其它 24.91 ms ·
最贵 `graph.subgraph` 13.30 ms。复算：`tests/_profile_frame.gd`。
与第二轮的 68.68 ms 属同一水平（绝对值随机器负载 ±5 ms），下面保留那一轮的 A/B，
因为它是**同会话内只改一处**的对照，比跨会话比绝对值有意义。

同一次会话内的 A/B（只改一处，其余不动）：

```
改动前  整帧 84.41 ms · steps=104 · 求值节点 85 · 框架/其它 25.94 ms
改动后  整帧 68.68 ms · steps=104 · 求值节点 85 · 框架/其它 23.60 ms   （1.23×）
```

两笔省下来的地方（都属框架，不是算子）：

| 项 | 之前 | 现在 | 做法 |
| --- | --- | --- | --- |
| 子图执行器 | 每帧新建（每个子图付一次「首跑价」） | 跨帧复用 | `_sub_runners` 挂在执行器上，ctx 只引用它 |
| 端口表 | 每帧 `clear()` 后重建，4.165 ms/帧 | 按「节点内容签名 + 目录修订号」复用 | `_ports()` 自带缓存，播放期参数不动 = 恒命中 |

改动后逐算子前五：

| 排名 | 算子 | 累计 | 占比 | 调用 |
| --- | --- | --- | --- | --- |
| 1 | `graph.subgraph` | 13.45 ms | 19.6% | ×2 |
| 2 | `image.recipe` | 4.88 ms | 7.1% | ×1 |
| 3 | `output.final` | 3.63 ms | 5.3% | ×1 |
| 4 | `image.bloom` | 2.31 ms | 3.4% | ×2 |
| 5 | `image.transform` | 1.91 ms | 2.8% | ×1 |

**`graph.subgraph` 的 13.45 ms 里只有 3–4.5 ms 是算子**，剩下的仍是框架：
子图内部 9 个节点也要各走一遍端口解析 / 输入解析 / 参数解析。
这条数字是 #4（主循环下沉）最直接的理由 —— 换个语言之前，先把「每步 0.23 ms 的调度」
这件事本身记清楚。

框架逐项（`tests/_profile_overhead.gd`，103 节点）：

```
hash(nodes)+hash(edges)          0.044 ms / 次
FxCatalog.ports × 103            4.165 ms / 帧   ← 已被 _ports 缓存吃掉，探针测的是裸成本
default_params + resolve × 103   1.256 ms / 帧
预览 capture × 55                2.365 ms / 帧
逐节点签名 × 103                 0.081 ms / 帧   ← 差量失效的代价，几乎免费
```

## 3.1 草稿帧：降画布到底省多少（2026-11-17，无头，示范工程 103 节点）

动态质量把「一帧」拆成两条并行的活：精确帧（全画布）与草稿帧（1/8 → 1/2 画布）。
草稿便宜多少**只能按同一口径量**，不能按像素数推算 —— 框架开销不随画布缩小。

| 档位 | 输出尺寸 | 求值中位 | 相对全画布 |
| --- | --- | --- | --- |
| 全画布（1.0×） | 192×108 | 44.6 ms | 1.00× |
| 草稿 1/2 | 96×54 | 29.7 ms | 1.50× |
| 草稿 1/4 | 48×27 | 23.3 ms | 1.91× |
| 草稿 1/8 | 24×14 | 21.9 ms | 2.04× |

复算：`tests/_bench_draft.gd`（每档热身一帧，三跑取中位）。这张表最重要的结论是
**「不是 64 倍」**：像素少 64 倍，时间只少 55%。1/8 档的 21.9 ms 里算子只剩几毫秒，
其余全是框架（索引、签名、端口表、分派）。所以草稿的收益是
**把画面首现时间从「一帧精确」压到「一帧框架」**，再往下压只能动框架本身（见 §7）。

换一个**算子很贵**的样本更能说明问题：示范工程改 `src_sheet.columns`（整表重排）时，
开窗实测草稿 **177 ms** 上屏 / 精确帧 **737 ms** 到位（`runtime_smoke` 的 F 段）。
4 倍差距全来自像素量 —— 那种场景下草稿才是真的救命。

### 3.2 草稿趟对**播放**的意义（2026-11-17 第四轮，开窗）

播放的推进条件是「下一帧有没有图」。没有垫图时，播放每帧都要等一次精确求值：

| 场景 | 只有精确帧 | + 草稿趟（1/8 画布，6 线程） |
| --- | --- | --- |
| 192×108，刚打开工程就按播放 | 每帧 45–52 ms（约 20 fps，画面一格一格跳） | 每帧 **38.5 ms**，2 秒走完 52 帧，画面连续（低画质） |
| 960×540，缓存只热了一半时按播放 | 每帧 **154 ms**（6.5 fps，几乎逐格停顿） | 每帧 **40 ms**（约 25 fps），垫图 57 帧、精确帧陆续替换 |

复算：`tests/_probe_play2.gd`（`FX_BENCH_MODE=cold` / `big`）。

草稿趟本身很快：192×108 的 60 帧工程，从「改参数」到「整段铺满黄格」约 **3 帧**
（`runtime_smoke` 的 F 段断言），之后精确帧在 1.5 秒内把 60 格全部换绿。
**这就是「改画布后看着像坏了」的正解**：不是等精确帧，而是先把整段变成能看的黄格。

## 4. 历史阶梯

| 阶段 | 整帧 | 相对最初 | 主要手段 |
| --- | --- | --- | --- |
| 纯 GDScript 逐像素 | 555 ms | 1.00× | — |
| 微观优化 + 行内并行（8 线程） | 344 ms | 1.61× | 内层循环展开、`map_rows` 按行切片 |
| + 原生内核 | 259 ms | 2.14× | 25 个通用图元进 C++ |
| + GPU 算子 | 226 ms | 2.46× | 模糊/混合/锐化/描边 compute |
| 现在 | **69.0 ms** | **8.0×** | + 每节点签名差量失效、子图执行器复用、端口表跨帧缓存 |

单算子倍数（192²）：遮罩 29.5×、变换 13.3×、波纹（GPU）30.4×；512² 遮罩 **128.8×**。

## 5. 看起来像提速、其实不是的

| 说法 | 实情 |
| --- | --- |
| 「Dead 剪枝能快 17.5%」 | Dead 18 是**结构上界**。拉取式求值本来就跳过不可达节点，剪掉的节点本来就没算。真实收益是常量折叠让 steps 3→2、汇点从 O(N) 变 O(汇点数)、以及可观测性。 |
| 「节点小图降质量能提速」 | 小图是在**已算完的全分辨率图**上 `duplicate()+resize()`，省的只是拷贝。实测 192² 抓小图 +0.3%、算子 1.0→0.5 +3.2%，都在噪声内。成本在「重算 8 个预览根 0.53s」。 |
| 「多线程按核数线性」 | GDScript 行内并行的天花板实测 **2.44×**（8 线程）。并行只贡献 1.34×。要一个数量级只能 GPU / GDExtension。 |
| 「GPU 一定比原生快」 | 512² 泛光 GPU 反而不如原生（10.4 vs 8.5 ms）：dispatch + 两次缓冲往返吃掉了收益。 |
| 「帧区间分段能提速」 | 示范工程的 3 条 `ease` 轨道每帧都变 → 31 段 / 0 帧可复用，**对这份工程零收益**。分段只对 `step` / 常量轨道有效。 |

## 6. 瓶颈归属

| 成本 | 归属 | 状态 |
| --- | --- | --- |
| `graph.subgraph` 14.1 ms | `core.graph` | `ctx.subgraph_runners` 每帧新建，9 节点子图每次付 ~4.7 ms 首跑价 |
| 框架 21.6 ms | `core.graph` + `core.render` | `_index_ports` 每帧重建（77 类型 × 103 节点）、每节点深拷贝默认参数、预览捕获 |
| `image.recipe` 4.7 ms | `core.recipe` | 仍是 GDScript 逐像素 |
| `output.final` 3.6 ms | `fx.composite` | 混合走原生，合成逻辑仍分多趟 |

## 7. 下一步（按收益排序）

1. **子图 runner 复用**：按子图内容身份缓存，省 ~4.7 ms/次；
2. **端口表改为按类型索引一次、跨帧复用**：省 ~4 ms；
3. **求值主循环下沉**（待办 #4 的 S1）：目标把 28% 框架压到 10% 以内；
4. **`recipe` / `bloom` / `final` 的逐像素段下沉**（S2）。
