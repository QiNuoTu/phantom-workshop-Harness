# 版本策略

> 四套号，各管一件事。混用会让读者把「能跑」读成「稳定」，把「接口没定」读成「承诺」。

## 1. 四套号

| 版本 | 存在哪 | 管什么 | 谁能改 |
| --- | --- | --- | --- |
| **应用版本** `app` | `version.json` → `app`；`project.godot` → `config/version` | 用户拿到的这个东西是哪个版本 | 发布者 |
| **内核契约版本** `kernel` | `version.json` → `kernel` | 插件能依赖的基座 API 是第几版 | 只在基座契约变化时 |
| **插件版本** `plugin` | 各 `plugins/<id>/plugin.json` → `version` | 这个插件自己迭代到哪 | 插件作者 |
| **工程格式版本** | `version.json` → `project_format`；`FxProjectArchive.HOST_VERSION` | `.fxproj` / `.fxgraph` 的字段含义 | 只在文件格式变化时 |

当前值：

```json
{ "app": "0.0.17-alpha", "kernel": "0.1.8", "project_format": "0.1" }
```

插件一律 `0.x.y`，并在清单里声明契约区间：

```json
"version": "0.1.1",
"contract": ">=0.1.0 <0.2.0",
```

`contract` 的意思：**这个插件只在这段内核契约内保证能用**。

## 2. 为什么必须分开

- **app 涨，插件不必涨**：修一个界面 bug，42 个插件不该集体 +1。
- **插件涨，app 不必涨**：用户单独装一个皮肤/节点包，不该影响产品号。
- **kernel 是唯一能判「这插件能不能装」的依据**：它一变意味着基座 API 变了，
  插件要么跟上，要么被 `contract` 挡在门外。

三个「1.0」互不相干、却在读者眼里拼成「成熟产品」——这是上一版最典型的失真。
现在 `0.x` 才是诚实：**当前是最初测试版，接口会变**。

## 3. 内核契约怎么涨

| 变化 | 幅度 | 例子 |
| --- | --- | --- |
| 新增可选贡献点 / 新增基座方法（有默认实现）/ 新增**带默认值**的参数 | patch `0.1.2 → 0.1.3` | 本轮：`FxBoot.error()` 增加可选 `scope` 参数 |
| 新增必须实现的契约、改方法签名、改语义 | minor `0.1.x → 0.2.0` | `FxRenderHost` 增加必须实现的方法 |
| — | — | 0.x 阶段**没有 major**，破坏性改动走 minor |

判定标准只有一条：**现有插件不改代码，能不能继续跑**。能 → patch；不能 → minor。

`0.1.2 → 0.1.3` 属于 patch：`error(where, message, scope := "")` 的第三个参数有默认值，
`errors()` 返回的字典只是**多了**一个 `scope` 键，读取方不读它也能工作。

因此 42 个插件的 `">=0.1.0 <0.2.0"` 仍然成立，**不需要**集体改区间。

## 4. 兼容区间写法

`FxContract.satisfies(版本, 表达式)` 支持（空格分隔多条，全部满足才算过）：

| 写法 | 含义 |
| --- | --- |
| `>=0.1.0 <0.2.0` | 显式区间（推荐） |
| `^0.1.0` | 0.x 时锁次版本 → `>=0.1.0 <0.2.0` |
| `~1.2.3` | 锁次版本 → `>=1.2.3 <1.3.0` |
| `1.2.3` | 精确相等 |
| `*` / 空 | 不约束 |

比较只看数字段，`-alpha` / `-beta` 参与显示不参与比较。

## 5. 工程格式

`HOST_VERSION = "0.1"`，`SUPPORTED_VERSIONS = ["0.1"]` —— **只认 0.1**。

- `host_version` 不是 0.1 的包（含早期的 `"1.0"`）**在读之前就拒绝**，
  提示「工程格式 X 已不再支持，请用旧版本导出成 `.fxgraph` 再打开」；
  不再有「仍要尝试加载吗？」那条路：拿新语义解释旧字段会把数据读坏，而且读坏了看不出来。
- 读不到 `host_version` 的包（更早的构建）仍按当前版本打开：**没有版本号 ≠ 版本不符**。
- 存盘只写 `0.1`；同一个路径连续保存不会追加（先写 `.tmp` 再换名）。
- 反向不兼容（旧构建打开新文件）不处理：alpha 阶段不做读入即迁移。
- `.fxgraph`（纯文本）没有包级版本，靠文档内的 `version` 字段自描述（内部修订号，不是语义化版本）。

## 6. 发布闸门（写死在这里，别靠记忆）

标 `alpha` 时，README 不得出现「可发布 / 生产可用 / 稳定」。

**GitHub Release 一律发成 Pre-release**（`prerelease: true`），不产生「Latest stable」。

- 0.x 阶段每一次 tag 都是试验品：接口、文件格式、性能都还会变；
- 发布页的 "Latest" 徽章会让下载者把它读成「稳定版」，与 README 的 alpha 声明自相矛盾；
- 历史 tag `v0.1.0` 的 Release 曾以正式版发布，**按本规则应改标 Pre-release**
  （网页端 Edit release → 勾选 "Set as a pre-release"）；
- 升 `beta` 之前，不得出现任何非 Pre-release 的 Release。

升 `beta` 需要**同时**满足：

1. `--fx-run=diag.blame` 汇总里**内核 0 条**；`diag.cache` 里没有「档位报高」的告警；
2. `bash tools/run_tests.sh` 0 失败，且断言数不低于上一版；
3. 示范工程 60 帧预渲染与播放实测数字写进 CHANGELOG（改前 / 改后）；
4. 「删掉任意一个插件后仍能启动」实测通过（不是静态断言）；
5. `python tools/check_docs.py` 返回 0；
6. README 双语的「待办进度」与代码一致。

第 5 条是本版新增：**数字必须由脚本核对**，不靠人肉同步。

`kernel` 只动了两次。

## 8. 什么时候动 1.0

不是「功能齐了」，而是：**插件契约连续两个 minor 没有破坏性改动，且存在第三方插件**。
在那之前，主版本号停在 0。历史 tag `v0.1.0` 是里程碑，其「可发布」的说法已撤回，
**不删 tag**（改写历史的风险大于收益），但任何文档都不得据此宣称稳定。
