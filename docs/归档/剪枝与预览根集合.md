## 2. 现象归类与根因

四个现象不是四个 bug，是**两条链**：

| 根因族 | 事实依据 | 导致的现象 |
| --- | --- | --- |
| **A. 单根求值** `runner.run()` 只 `_eval(output_id)`；`FxPixelKit.size_of()` 只认 `image` 输入或 `ctx.canvas` | `plugins/core.graph/fx_graph_runner.gd:75`、`plugins/core.pixels/fx_pixel_kit.gd:11` | ② 生成器只吃画布；③ 旁支没预览；④ 数值节点没有输出可读 |
| **B. 画布写入无防抖、无预算提示** SpinBox 每次 `value_changed` 直接 `mutate(["canvas"])`，`MAX_CANVAS=4096` | `plugins/editor.document/fx_document_panel.gd:118,156`、`plugins/core.graph/fx_graph_doc.gd:21` | ① 改宽高卡飞 |

**「预览有时候有 bug」的第三个来源**（本轮额外查出）：

- `start_preview_pass()` 在 `cache.stats().missing > 0` 时直接 return，整段精确帧没算完就不跑缩略图趟；
- 播放时 `quality.preview_scope = selection_output` 会把 `_capture_preview()` 的白名单缩到「输出 + 选中」，
  展开的旁支节点即使被求值也会被挡在捕获之外。

所以「有时候」= 取决于那一刻在不在播、精确帧补完没有、选中了谁。三条都修了，见 §3。

## 4. 活节点定义（剪枝的冻结标准）

```
Live = Reachable(output_id)
     ∪ ⋃ Reachable(r)  for r ∈ preview_roots
     ∪ ⋃ Reachable(s)  for s ∈ sinks      { def(s).evaluate_always }
     ∪ ⋃ Reachable(e)  for e ∈ exec_nodes { def(e).has_exec_in }
```

- `Reachable(x)` = 从 x 沿**入边反向**走到的全部节点（x 自己也算）。
- `preview_roots` 由编辑器给出：展开的节点 ∪ 当前选中节点，随 job 快照进工作线程。
- `evaluate_always` 汇点里含 **6 个 `godot.export` 导出节点**（写文件副作用），
  因此**一个都不能剪**；它们自己要跑，其上游也必须算活，否则汇点求值会拉到空输入。
- `exec_nodes` 由 `_exec_entries()` 无条件驱动，同样必须连同上游一起算活；
  漏掉它们会「上游被剪、执行流读到空值」。
- **不在 Live 里的节点才允许被剪掉**。仅看 `output_id` 的剪枝是错的：它会删掉用户正在看的旁支。

> 这两处精确化是**实现时发现的语义要求**，不是放宽标准：原公式里的
> `∪ {n | evaluate_always}` 只列出了汇点本身，没有把它们的依赖算进来，
> 而执行器对汇点是 `_eval(s)`（会递归拉上游）。IR 忠实还原执行器行为，因此把
> `Reachable(s)` 写进公式。执行流节点同理。

### 边界验算

| 情形 | `Live` 规模 | 剪枝收益 |
| --- | --- | --- |
| 只有输出链，无展开、无汇点 | `|Reachable(output)|` | 最大 |
| 用户展开全部节点（103 节点示范工程全展开） | ≤ 103（全图） | **0**，此时剪枝必须自动退化为「不剪」 |
| 播放中 `preview_scope=selection_output` | 输出链 ∪ 选中 ∪ 展开 | 展开节点仍保留，不因画质策略被剪 |

上界公式：`|Live| ≤ |Reachable(output)| + Σ|Reachable(r)| + Σ|Reachable(s)| + Σ|Reachable(e)|`，
最坏情形等于全图节点数。所以「剪枝能省多少」必须先量，不能承诺固定百分比。

**103 节点示范工程实测**（`diag.compile` / `tests/test_core_compile.gd` 可复算）：

| 量 | 实测 | 说明 |
| --- | --- | --- |
| 节点 / 连线 | 103 / 81 | 拓扑序 103，环 0，类型不匹配 0 |
| `Reachable(output)` | **39** | 输出链本身只覆盖 38% 的图 |
| 汇点 / 执行流 | 19 / 4 | 把 Live 拉高，这是「汇点必须保留」的代价 |
| `Live` / `Dead` | **85 / 18** | 结构剪枝上界 **17.5%** |
| 时间无关 / 编译期折叠 | 39 / **2** | 只有 2 个纯标量静态节点能预算成常量 |

输出链虽只有 39 个节点，19 个汇点的依赖闭包把 Live 顶到 85 —— 这正是上界公式说的
「最坏情形接近全图」。**17.5% 是「理论上可以不参与」的上界，不是实测提速**：拉取式
求值本来就跳过了 Dead 节点，本轮真实收益主要在常量折叠、汇点按拓扑序遍历、以及
第一次把「哪些节点活着」变成可查的事实。

### 与「无关键帧节点」的关系

用户第 3 条还要求「没有关键帧的节点不参与运算」。这与 `Live` 是**两个维度**：

- `Live` 决定「哪些节点属于本帧的计算图」（结构剪枝）；
- 无关键帧 + 时间无关 → 可进**跨帧静态缓存**（值复用，不是删除）。

顺序建议：先按 `Live` 删结构，再对 `Live` 里时间无关的子图做常量折叠/静态缓存。
两者混在一起做，会让「用户展开了一个静态节点却看不到值」再次变成偶发 bug。

## 5. 内存预算（可复算）

```
frame_bytes = W × H × 4            (RGBA8)
segment_MiB = W × H × 4 × N / 2^20 (N = round(duration × fps))
```

| W×H | N | 单帧 | 整段 | 说明 |
| --- | --- | --- | --- | --- |
| 128×128 | 30 | 0.0625 MiB | 1.875 MiB | 默认，无感 |
| 1024×1024 | 60 | 4 MiB | 240 MiB | 提示阈值附近 |
| 4096×4096 | 60 | **64 MiB** | **3840 MiB ≈ 3.75 GiB** | `MAX_CANVAS` 上界，单线程也会 OOM |

旧实现拖动 SpinBox 从 128 到 4096 若产生 20 次提交，就是 20 次「换桶 + 全分辨率重算」；
新实现 1 次。**防抖只解决连续提交，不解决最终尺寸本身过大**——那是第 2 条
「预览低质量管线」要做的事（交互期降采样、精确档再上全分辨率），本轮未做，见 §7。

## 9. IR 编译计划（第四轮实现）

### 9.1 为什么是「计划」而不是「新执行器」

用户建议把节点图降级成 DAG / 指令序列、做类型检查、常量折叠、无用节点剔除，
再走字节码 VM 或 GPU 管线。本轮只做了**前置的编译层**：它不改变任何算子的求值语义，
只回答「本帧哪些节点要跑、哪些结果可以直接取常量」。

理由：实时预览与最终渲染必须共用一套求值语义。若先换执行层再补语义对齐，
「预览和导出不一致」会变成一整类新 bug。编译层先落地，VM / WGSL 才有可对照的基准。

### 9.2 计划长什么样

`FxIRCompiler.compile(doc, roots) -> Dictionary`，纯数据，键：

| 键 | 含义 |
| --- | --- |
| `order` | 拓扑序的指令序列（Kahn，依赖在前） |
| `live` / `dead` | 按 §4 判活算出的集合 / 可剪节点列表 |
| `sinks` | 所有 `evaluate_always` 汇点（拓扑序），**一个都不剪** |
| `exec_nodes` | 执行流节点，同样作为根 |
| `static_nodes` | 时间无关子图（可跨帧复用，**不是删除**） |
| `foldable` / `constants` / `fold_params` | 编译期预算出的纯标量常量及其参数快照 |
| `type_errors` / `cycles` | 端口类型不匹配、无法拓扑排序的部分 |
| `ids_hash` / `signature` / `stats` | 计划与文档的绑定键、结构指纹、统计 |

`constants` 只收标量类输出（数值 / 向量 / 颜色 / 字符串 / 布尔 / 这些的数组），
**绝不预算 Image / Object**；候选还必须是无入边、无关键帧、`cacheable`、非 exec、
非汇点、非 gpu、且算子预算期间没有产生任何警告。任一条件不满足就不折叠，求值器照常调算子。

### 9.3 三条求值路径共用同一份计划

```
FxRenderService._plan_for_current_doc()
   ├─ FxCapabilities.providers("graph.compile")[0].apply → FxIRCompiler.compile
   └─ 按 (store.content_key(), 预览根集合) 缓存，不是每帧重编译
        ├─ 同步路径  _render()      → runner.compile_plan
        ├─ 工作线程  _submit() job → FxRenderWorker → runner.compile_plan
        └─ 后台预渲染 prefetch job → FxFramePrefetcher → runner.compile_plan
```

- 渲染服务只认**字符串能力键 + 数据字典**，不认识 `FxIRCompiler` 这个类名。
  停用 `core.compile` → `providers()` 为空 → 计划为 `{}` → `FxGraphRunner` 的所有新分支关闭，
  行为与改造前逐字一致。这正是「删掉任意一个插件仍能启动」的实测路径。
- 计划只绑定**节点 id 集合**（`ids_hash`），不绑定参数值：改参数仍复用计划；
  换工程 / 增删节点会立刻失配，求值器 `_plan_matches()` 整份作废，不误剪新文档。
- `run()` 的汇点循环在有计划时按拓扑序遍历 `sinks`，省掉每帧一次全图线性扫描；
  无计划时保留原来的全图扫描分支。

### 9.4 求值器消费点

| 位置 | 行为 |
| --- | --- |
| `_eval()` 开头 | `dead` 短路（不跑算子）；`constants` 命中则直接返回，仍调 `_capture_preview()` 保证数值读数不丢 |
| `run()` 末尾 | 按 `sinks` 拓扑序补跑汇点 |
| `_last_stats` | 多带 `pruned` / `folded` / `plan_live` / `plan_dead`，可从状态栏与诊断读到 |

测试 `tests/test_core_compile.gd` 的 28 条断言覆盖：拓扑序、Live/Dead、汇点保留
（含导出副作用节点，只编译不求值）、常量折叠结果、两条路径**图像逐像素一致**、
`steps 3 → 2`、计划失配自动关闭、空计划原行为、类型不匹配与环检测、示范工程 103/81。

### 9.5 诚实的边界

- **结构剪枝在拉取式求值器里收益天然有限**：Dead 节点本来就不会被 `_eval` 拉到；
  真正的收益是常量折叠、汇点有序、以及把「谁活着」变成可查事实。别把 17.5% 当提速。
- ~~时间相关性判定过粗 / 帧区间分段没做~~ → **第五轮已做帧指纹分段**（§9.6）。
  `_build_time_dependence()` 的判定保留原样（其它逻辑仍读它），跨帧缓存改由
  「签名 + 帧指纹」共同判定，绕开了粗判定而不破坏既有语义。
- **执行流修剪仍未做**：时钟闭包把示范工程 72 个节点排除在按段缓存之外，
  这是「没关键帧的节点不参与运算」剩下的主要工作，仍属插件层。
- **编译期折叠只覆盖纯标量节点**：示范工程里只有 2 个。图像类算子的常量折叠需要
  解决「预算一张全尺寸图比不预算更贵」，不能用同一套规则。
- IR 目前是**数据计划**，不是字节码；VM / WGSL / GDExtension 都还没做。

## 9.6 帧区间分段：帧指纹（第五轮）

### 9.6.1 判据

把「哪些帧可以复用上一帧的结果」化成一个等价条件：

```
frame_key(t) = 全图所有轨道在 t 的采样值序列
两帧 key 相同 ⇔ 所有轨道采样值相同 ⇒ 不直接读时钟的节点输出必然相同
```

`FxTracks.key_of(tracks, t)` 是**唯一实现**：`core.compile` 用它做编译期报告，
`FxGraphRunner` 用它在 `_begin()` 里按**实际 `ctx.t`** 算本帧指纹（不用整数帧号，
否则交互时播放头落在两帧之间会被近似到错误的段）。

这一步同时解决两件事：

- **无关键帧 / 单帧常量轨道**：`plan_tracks` 为空或采样值恒定 → 全时间轴只有 1 段 →
  除时钟/执行流节点外整图只算一次；
- **帧区间分段**：`step` 保持段、文本/布尔轨道、到达终点后的保持段自然得到相同 key，
  无需显式维护区间表；`linear` / `ease` 段每帧 key 不同，照常逐帧算。

### 9.6.2 运行时怎么用它

`FxGraphRunner` 的跨帧静态缓存从「`sig` 相同即复用」升级为：

```
命中 = static_cacheable 且 sig 相同 且 cached.frame_key == 当前 frame_key
```

`use_cache` 判定放宽为 `use_cache or plan_relaxed`，其中

```
plan_relaxed = 有计划 且 node ∉ clock_nodes 且 node ∉ volatile
clock_nodes  = {时钟算子 / exec / 汇点 / gpu / 非 cacheable} 的下游闭包
```

时钟闭包是安全边界：这些节点直接读 `ctx.t` 或依赖每帧变化的执行状态，
即使轨道采样值不变也可能变，必须排除。`volatile` 闭包比它更宽，一并排除。
缓存命中时恢复 `node_params` / `node_values`，参数与数值读数不丢。

**空计划时** `_frame_key` 恒为 `""`、`plan_relaxed` 恒为 false，
命中条件退化为原来的「`sig` 相同」，行为逐字不变。

### 9.6.3 计划新增的键

| 键 | 含义 |
| --- | --- |
| `plan_tracks` | 全图轨道定义（供运行时按实际 t 重算指纹） |
| `clock_nodes` | 时钟/执行流/汇点/gpu/非 cacheable 及其下游闭包 |
| `frame_stats` | `frames` / `tracks` / `distinct_keys` / `reusable_frames` / `clock_nodes`，按整数帧预采，只用于报告 |

`diag.compile` 会打印：`帧指纹：60 帧 / 3 条轨道 / 31 个不同段（可跨帧复用 0 帧）· 时钟节点 72`。

### 9.6.4 实测（不要夸大）

| 图 | 帧 / 轨道 | 不同段 | 可复用帧 | 结论 |
| --- | --- | --- | --- | --- |
| 合成 `step` 轨道 | 10 / 1 | 2 | **8** | `segment_hits = 8`，数值读数逐帧与未剪枝路径一致（前段 3、后段 6） |
| 单帧常量轨道 | 10 / 1 | **1** | **9** | 常量轨道就是一段，整段只算一次 |
| 103 节点示范工程 | 60 / 3 条 `ease` | 31 | **0** | `ease` 每帧都变，**本轮对它没有直接提速** |

示范工程 3 条轨道全是 `ease` 插值，采样值每帧不同；时钟闭包还排除 72 个节点。
所以「帧区间分段」是**针对常量/step 轨道的正确性优化**，不是普适提速。
把它写成「性能提升 X%」就是新一轮的「说明与事实不符」。

`reusable_frames` 衡量的是「轨道采样值与上一帧相同的帧数」，**不是整体缓存命中率**：
无关键帧的节点本来就能被原有 `_static_cache` 永久复用，不在这项统计里。

### 9.6.5 仍未做

- **执行流修剪**：`clock_nodes` 目前把执行流节点及其全部下游一刀切排除，
  没有区分「循环索引每帧变」与「常量执行链」。缩小时钟闭包是下一步。
- IR 仍是数据计划，不是字节码；VM / WGSL / GDExtension 未做。
## 10. 节点值预览：按类型分类（第六轮）

### 10.1 为什么不是一行文字

旧实现把非图像输出压成 `"number = 5.0"` 这样一行灰字推到卡片上。
问题是这一类信息**只能读、看不出趋势**：噪声、振荡、饱和、逐帧抖动，
全都变成「一个会变的数字」。用户的原话是「不同数值类型要看不同的东西」。

所以读数改成**结构化**的，画法按端口类型分派：

| 端口类型 | 画法 | 看什么 |
| --- | --- | --- |
| `number` | 迷你曲线（最近 48 个采样）+ 三位小数 | 趋势：在涨、在振荡、饱和了 |
| `vec2` | 方框 + 十字 + 端点 | 方向与幅度（±1 归一，超出贴边） |
| `color` | 棋盘底 + 实色覆盖 + `#rrggbb` | 颜色本身，含透明度 |
| `bool` | 状态灯（亮=开） | 一眼看清通断 |
| `string` | 等宽截断文本 | 文本内容 |
| 其它（数组/字典） | 文本兜底 | 至少知道算出了什么 |

### 10.2 数据形状

```jsonc
// node_values[node_id]
[
  {"port": "out", "type": "number", "value": 3.5, "text": "3.500"},
  {"port": "flag", "type": "bool", "value": true, "text": "开"}
]
```

- `type` 来自**端口声明**（插件自己给的），不是猜的 Variant：`int` 落在 `number` 端口里
  仍按曲线画。
- 没有 `type` 的第三方插件按值形态兜底（`float/int`→数值、`Vector2`→向量、`Color`→颜色、
  `bool`→布尔、其余→文本），不会退化成空白。
- 最多 4 项；`Image` 走预览图通道，`Object`/`Dictionary` 跳过。

### 10.3 分派在哪儿（谁的问题归谁）

| 层 | 负责 | 文件 |
| --- | --- | --- |
| 执行器 | 收读数、带端口类型；**不受 `capture_previews` 影响** | `core.graph/fx_graph_runner.gd:_value_samples()` |
| 呈现器 | 原样转发（不认识类型） | `core.render/fx_render_service.gd` |
| 编辑器 | 转发给卡片，不认识类型 | `editor.graph/fx_graph_editor.gd` |
| 卡片 | **按类型画** | `editor.graph/fx_node_value_gauge.gd` |

`kind_of()` 是唯一的分类点：只认端口类型名与 Variant 形态，**不认识任何节点类型**。
新增插件节点不需要改这里 —— 端口类型是插件声明的。

### 10.4 三条不显眼但会咬人的约束

1. **读数与 `capture_previews` 解耦**。旧实现把两者绑在一起，播放期一关小图，
   数值卡片就整片空白。`capture_previews` 省的是「缩小一张图」，读几个 Variant 不花钱。
2. **只在显示会变时重绘**。播放期读数每帧推送，无条件 `queue_redraw()` 会让十几张卡片
   每秒各重绘 60 次。判据是「显示签名」：`port|kind|text` 拼起来，一样就不画。
3. **值没变不追加采样**。否则静止画面会把 48 个格子全填成同一个值，曲线被「挤成一条直线」
   （其实是看不出它一直没变）。

## 11. 两条预览管线（第六轮·用户第 2 点）

### 11.1 拆成两条，而不是一条调参

| | 节点小图 | 输出预览 |
| --- | --- | --- |
| 用途 | 卡片上「大概长什么样」 | 就是交付的那一帧 |
| 分辨率 | 可降（`quality.preview_limit`，16..512） | **不降**（内核把 `output_downscale` 钉死为 false） |
| 算子质量 | 可降（`quality.preview_operator`） | 恒精确 |
| 刷新 | 可慢（`quality.preview_refresh_ms`，默认 1500ms） | 每帧 |
| 落地 | 缩略图趟（`preview_only` job） | 主渲染 + 预渲染（写精确帧缓存） |

这条边界不是「性能优先」的妥协，而是**结论可信**的前提：
用户按导出按钮拿到的东西，必须和屏幕上看到的一致；能让步的只有卡片上的小图。

### 11.2 修掉的三处「设置写了但没用」

| 现象 | 真相 |
| --- | --- |
| 「节点预览边长」调到 192 没反应 | 后台两趟（缩略图、预渲染）都写死 `PREVIEW_THUMB = 72`，只有主线程那条路读设置 |
| 想调小图糊一点/准一点，没地方调 | 缩略图趟的算子质量被写死 `0.5`（`quality=0` 时由预取器推导），没有独立旋钮 |
| 缩略图刷新太勤/太懒都改不了 | `_preview_pass_clock = 1.5` 写死 |

现在两项新设置（`quality.preview_operator` 默认 0.5、`quality.preview_refresh_ms` 默认 1500）
**默认值等于旧行为**，所以升级本身不提速也不降质；变的是「调得动」。
`diag.cache` 新增一节把两条管线的当前参数打出来，免得再出现「以为在调、其实没接线」。

### 11.3 实测：这份工程上它几乎是免费的（诚实零结果）

`tests/_bench_preview.gd`（示范工程 103 节点 / 192×108 / 8 个预览根，开窗跑）：

| 组 | 192×108 | 512×512（趋势参考，非基准） |
| --- | --- | --- |
| A 小图边长 16（≈无小图） | 534.6 ms | 5518.2 ms |
| B 小图边长 128 · 算子 1.0 | 536.2 ms | 5433.8 ms |
| C 小图边长 128 · 算子 0.5 | 553.5 ms | 5376.5 ms |
| 抓小图的代价（B−A） | **+0.3%** | **−1.5%** |
| 小图算子档 1.0→0.5（C−B） | **+3.2%** | **−1.1%** |

**结论**：在这份工程上，抓小图与降小图算子档都在噪声范围内（±3%）。
原因是成本根本不在这里——一次缩略图趟要 0.53 s，是因为它**要把 8 个预览根整条重算一遍**，
而缩放+拷贝只占个零头。所以：

- 本轮**没有**给这个工程提速，不能写成「性能优化 X%」；
- 真正的杠杆是「别白算这一趟」：`previews.has_frame(want_index)` 已在挡重复趟，
  但播放期 `preview_scope` 收窄后仍会补趟 —— 这是下一步该压的地方；
- 旋钮的意义在大画布与「设置被忽略」这两件事上，不在 192×108。

### 11.4 两个测量口径坑（都踩过）

1. **`capture_previews=false` 不是「只算输出」**。关掉捕获后预览根不再算作求值根，
   实际求值集合变成输出链 —— 和「抓小图」不是同一批节点。第一版实测因此得出
   「抓小图快 60%」的荒谬结论。要比就必须同根、只改一个变量。
2. **首轮包含 shader 编译**（示范工程含 `core.shader` 节点，约 0.85 s）。
   不预热的话「第一组」永远被这 0.85 s 污染，看起来像「边长 16 比 128 慢一倍」。
   脚本里已加一次丢弃的预热，并把这两条写进注释。

## 12. 逐层分辨率档：实现层说明（第七轮）

### 12.1 为什么不是「给每个算子加一个 scale 参数」

算子有 40 多个插件里的一大堆，逐个改既不可能也违背边界。实际上**不需要**：

- 算子决定输出尺寸，要么读 `ctx.canvas`（生成器），要么跟随输入图尺寸（滤镜）；
- 所以只要「给算子一个更小的画布 + 给它更小的输入图」，算子就自动在低分辨率下工作。

于是实现只有两处：`_eval()` 在调算子前把 `ctx.canvas` 换成该档的画布，
`_resolve_inputs()` 在跨档取图时重采样。**算子一行都不用改。**

### 12.2 画布视图：save / restore，靠「相等就不动」避免重复缩

```gdscript
var want := _canvas_for(scale)
var saved := ctx.canvas
if want != saved: ctx.canvas = want
...   # 求输入（递归，上游各自 save/restore）、采样参数、调算子
if want != saved: ctx.canvas = saved
```

关键在 `want != saved` 这个判断：同区段内所有节点算出的 `want` 相同，
所以只有**区段入口**会真的换画布，内部节点发现「已经是这个尺寸」就不动。
少了这条判断，0.5 档的 3 节点链会缩三次（0.125），画面直接废掉 —— 第一版就是这么错的。

### 12.3 跨档取图：按比例还原，不需要知道原始尺寸

`ratio = 下游档 / 上游档`，`size × ratio`。降 0.5 再乘 2 就回来了，
中间经过几段也不会累积误差（每段各自四舍五入，误差 < 1px）。

- 缩小（`ratio < 1`）用 `INTERPOLATE_LANCZOS`：代理分辨率只允许**一次**降采样，
  BILINEAR 在细线条上会走样，而这一步的代价远小于它省下的全分辨率算子。
- 放大（`ratio > 1`）用 `INTERPOLATE_BILINEAR`：单次放大用 LANCZOS 会产生振铃。

### 12.4 区段模型与「共享上游不被拖下水」

传播规则：声明者 N(s) 向上游走，遇另一个声明者就停。

但只有「降档需求」的传播不够 —— 还必须有**全分辨率需求的传播**：

```
从 output / 汇点 / 预览根 出发，按 1.0 向上游走，遇声明者停
然后让每个声明者按自己的档位向上游走
最终每个节点取所有需求里的**最大值**
```

为什么要有第一步：同一个节点如果还被一条全分辨率路径消费，它必须按 1.0 算，
降档由消费方在边界缩放。少了这一步，一条旁支的降档会**悄悄拉低主干精度** ——
这类问题不会报错、不会崩，只会让画面「说不上哪里糊」，是最难查的一类。

### 12.5 像素单位参数按 `unit: "px"` 换算

`nodes.json` 的参数早就有 `unit: "px"` 字段（`radius` / `offset` / `cell` / `size`），
执行器按它乘 `ctx.eval_scale`：0.5 档下 `radius=4` → 2。

不换算的话，0.5 档下 `radius=10` 的视觉效果等于全分辨率的 20 ——
那不是「画质略降」，是**效果变了**，比不降还糟。

`ctx.eval_scale` 的存在也是给算子自己用的：将来有算子需要按档位调整采样步长，
读它就行，不必让执行器认识具体算子。

### 12.6 三个坑

1. **子图要跟着降**。外层给了半尺寸输入、子图内部却按全尺寸算，出来还得再缩一次，
   档位收益全丢在边界上。做法是子图 runner 的 `base_scale = ctx.eval_scale`。
2. **输出节点与汇点必须拒绝**。它们降了，交付画面/导出文件就变小了。
   拒绝信息进 `scale_report["refused"]` —— 「我设了为什么没生效」只有这一个答案。
3. **`res_scale` 是内容不是布局**。`content_of()` 里不能像 `pos` 那样抹掉，
   否则改了档位不换桶、画面不更新。但值为 1.0 时要抹掉，
   否则「调回全分辨率」会白重建一次。

## 13. 一帧 555ms 花在哪：算子里的逐像素循环（第八轮）

### 13.1 先把归属量出来，别靠猜

第一反应是「框架开销大」——每帧重建端口表、对整份文档做递归哈希、预览图拷贝。
逐项测下来**全错**：

| 项 | 实测 / 帧 |
| --- | --- |
| `hash(nodes) + hash(edges)`（整份文档递归哈希） | 0.043 ms |
| `FxCatalog.ports × 103`（端口表全量重建） | 4.2 ms |
| `default_params + 轨道采样 × 103` | 1.2 ms |
| 预览捕获（55 次 duplicate + resize） | 2.5 ms |
| 逐节点签名 × 103 | 0.09 ms |

加起来不到 8 ms。真实分布（`tests/_profile_frame.gd`）：

```
整帧 597 ms · 算子累计 559 ms（93.7%）· 框架/其它 37.6 ms
```

所以优化只能落在算子上，而且是算子里的**逐像素循环**。

### 13.2 两个真正的成本源

把 bloom 的五段拆开量（`tests/_bench_bloom.gd`）：

| 段 | 耗时 |
| --- | --- |
| `duplicate + get_data` | 0.001 ms（惰性 COW，几乎免费） |
| 阈值化（串行，原实现） | 11.3 ms |
| 阈值化（按行并行） | 8.4 ms（只快 25%） |
| 两次 resize（8 倍缩→放） | 0.44 ms（引擎 C++，很便宜） |

并行只快 25%，说明瓶颈不是「一个线程干不完」，而是**每个线程自己就慢**。原因有两条：

1. **内层小循环**：`for c in range(3)` 每像素执行 3 次循环迭代，GDScript 每次迭代都要付解释器开销。
   展开成三行赋值后，同一段从 11.3 ms 降到 4 ms 级。
2. **对象构造与函数调用**：`FxImageUtil.luma(Color(r, g, b))` 每像素构造一个 Color；
   `rgb_to_hsv` / `hsv_to_rgb` 是二十来条 GDScript 字节码。换成引擎的 `Color.h/s/v` 属性
   与 `Color.from_hsv()`（C++ 实现）后，`image.hue` 从 56 ms 降到 10 ms 以内。

### 13.3 落地的两件事

**（1）行内并行**（`FxPixelParallel`）

按行把像素循环切片，各线程只写自己那几行，拼接一次 `append_array`。

- 只在**主线程**启用：预渲染本身按帧并行（2–6 线程），worker 里再往同一个
  `WorkerThreadPool` 提交子任务会把池占满 —— 几条线程互相等对方的子任务就是死锁。
- 线程数按**像素量**给（每线程约 2k 像素起，上限 8）：按核数给会让小图过度并行，
  唤醒与拼接的开销吃掉全部收益。
- 小图（< 16384 像素 / < 24 行）直接串行。
- `FX_NO_PARALLEL=1` 可全局回落串行，用来做 A/B 与排查「并行之后画面不对」。

接入的三处都是「一改覆盖一片」的公共入口：

| 入口 | 覆盖 |
| --- | --- |
| `FxPixelKit.map_rows` / `generate_rows` | 色相/色调/色阶、渐变/形状/光栅等生成器 |
| `FxPixelKit.remap_rows` / `sample_rows` | wave / swirl / ripple / displace 等重映射 |
| `FxImageUtil._blend_bytes` | `output.final` 每层、`blend2`、阴影、遮罩、文字合成 |

**（2）微观优化**（同一批循环里顺手做的）

- 三通道内层循环展开成三行；
- `int(round(x))` → `int(x + 0.5)`（这些值恒非负）；
- 双线性采样从「4 通道 × 3 次 `lerpf` = 12 次函数调用/像素」改成「4 个权重一次算完」；
- `Color` 构造与 HSV 换算改走引擎 C++。

### 13.4 实测（示范工程 103 节点 / 192×108，开窗，中位值）

| 配置 | 整帧 | 相对基线 |
| --- | --- | --- |
| 优化前 | 555 ms | — |
| 只做微观优化（`FX_NO_PARALLEL=1`） | 460 ms | **1.21×** |
| 微观 + 行内并行 | 344 ms | **1.61×** |

单项（累计耗时）：

| 算子 | 优化前 | 优化后 | 倍数 |
| --- | --- | --- | --- |
| `image.bloom` | 72.8 ms | 14.2 ms | 5.1× |
| `image.hue` | 56.1 ms | 9.5 ms | 5.9× |
| `image.wave` | 61.1 ms | 23.7 ms | 2.6× |
| `output.final` | 32.9 ms | 16.5 ms | 2.0× |
| `image.blend2` | 28.6 ms | 13.9 ms | 2.1× |

### 13.5 为什么只有 1.6×，不是 3–4×

**GDScript 的并行效率远低于核数**：8 线程跑纯算术循环，实测只有 **2.44×**
（`tests/_bench_parallel.gd`）。这是解释器与内存带宽的共同上限，不是参数没调对。

所以「按核数线性加速」在这里不成立。真正的收益来自**减少每条指令的成本**
（展开、去函数调用、走 C++），并行只是在此之上再叠 1.3×。

要继续上一个数量级，只有两条路：

1. **GPU**：`render.gpu` 已覆盖 `image.blur` / `image.mix` / `image.outline`，
   实测开窗下描边从 47 ms 降到榜外。把 bloom / wave / hue 也搬过去是下一步的第一选项。
2. **GDExtension**：把像素内核用 C++ 写，代价是可移植性与维护成本。

### 13.6 三条纪律（都是这一轮踩出来的）

1. **改逐像素循环必须与串行**逐字节**比对**，不能只看「看起来一样」。
   切片边界差一行、读写索引没分开，画面只会在某些尺寸上烂一点点。
   `tests/test_pixel_parallel.gd` 的 17 条断言做的就是这件事（含 25/37/101 行这种除不尽的尺寸）。
2. **「以为在并行」是最大的坑**。`FxPixelParallel.parallel_calls` / `serial_calls` /
   `last_threads` 三个计数器就是为了让「静默回落串行」不可能被忽略。
3. **子图耗时不会自动汇总**。子图执行器有自己的 `ctx`，不合并就只看到
   「graph.subgraph 80ms」这一个黑盒（现在 `fx_ops_subgraph` 会把内部耗时合并回来，
   键带子图文件名前缀，诊断里单独列、不与父级相加）。

# 成本归属（要开窗：示范工程含 shader 节点）

## 14. 两条加速路径：GPU compute 与原生内核（第九轮）

上一轮把 GDScript 的逐像素循环压到 1.61×（555 → 344 ms），天花板很清楚：
**GDScript 的并行效率只有 2.44×**（8 线程实测），循环体里每条指令都要过解释器。
要再上一个数量级，只有两条路 —— 而它们**互补，不是二选一**：

| | GPU compute（`render.gpu`） | 原生内核（`extensions/pixel_native`） |
| --- | --- | --- |
| 生效条件 | 有图形设备、非无头、能走渲染线程 | 扩展编出来并加载（无头也生效） |
| 适合 | 大画布、算子数学简单 | 任何尺寸、任意线程、含不可并行的边界逻辑 |
| 代价 | 每次 dispatch 有固定开销；工作线程要跨线程桥 | 需要 C++ 工具链与 ABI 对齐 |
| 缺席时 | 回落 CPU 算子 | 回落 GDScript 实现 |

所以分工是：**GPU 干大图的活，原生内核兜住所有尺寸与无头环境**。
两条都不改变语义：拿不到就走原来的 GDScript。

### 14.1 GPU：一个着色器承载多个 op

`FxGpuCompute` 本来就有 `blur / mix / outline / sharpen`，这轮补了三个：

| op | 算子 | 说明 |
| --- | --- | --- |
| 5 | `image.bloom` 阈值趟 | 亮度阈值 + smoothstep，cfg[8] = 阈值×1000 |
| 6 | `image.bloom` 叠加趟 | 底图 + 泛光×强度（强度可到 3.0，走 cfg[8] 而不是 amount） |
| 7 | `image.hue` | RGB↔HSV 在着色器里做，与引擎同一套公式 |
| 8 | `image.wave` | sin 位移 + 双线性采样，float 位模式由 `uintBitsToFloat` 还原 |

两个坑值得记：

1. **负参数不能按 uint 读**。cfg 是整型缓冲区，`-0.1` 按 `float(cfg[8])` 读会变成
   4294966xxx，整个画面直接刷白。必须 `float(int(cfg[8]))`。
2. **带小数的参数不能乘 1000 打包**。波形的相位可能上千，乘 1000 会溢出且丢精度，
   改成把 float 的位模式塞进整型槽（GDScript 侧 `PackedFloat32Array(...).decode_s32(0)`）。

### 14.2 原生内核：只做「通用图元」，不认识节点

`FxPixelNative`（`extensions/pixel_native`）挂在 `core.pixels` 的 `FxNativeBridge` 后面，
只暴露七个哑接口：

```
hue(src, shift, sat, val)              tint(src, color, amount, preserve_luma)
bright(src, threshold)                 bloom_add(base, glow, amount)
wave(src, amp, omega, phase, axis)     remap(src, coords)
affine(src, offset, scale, rot, anchor, wrap)
mask_image(src, mask, channel, invert, softness, opacity)
blend(base, top, rect, at, mode, opacity)     ← 原地合成
```

**没有一个参数是节点类型或参数名**。所以新增节点不用碰 C++，而「同一份公式两处实现」
的风险由测试兜住（见 §14.4）。

接入点是三个「一改覆盖一片」的公共路径：

| 原生接口 | 覆盖的算子 |
| --- | --- |
| `blend` | `output.final` 每层、`image.blend2`、阴影、遮罩、文字合成 |
| `wave` / `affine` / `remap` | 波纹、旋转缩放、任意坐标重映射类 |
| `hue` / `tint` / `bright`+`bloom_add` / `mask_image` | 调色、着色、泛光、遮罩 |

线程数**由调用方显式给**：主线程给到核数（上限 8），预渲染工作线程给 1 ——
它们本来就按帧并行，再各自开满线程只会互相抢核。

### 14.3 精度约定（这轮最费时间的地方）

GDScript 的 float 是 **64 位**，而引擎 `Color` 的通道是 **32 位**。照着公式抄不够，
得知道每一步落在哪一侧：

| 步骤 | 位宽 |
| --- | --- |
| 读字节 → 归一化、乘加、clamp、`int(x*255+0.5)` | double（GDScript 侧） |
| `Color(r,g,b,a)` 构造、`get_hsv()`、`from_hsv()`、`lerp()` | float（引擎侧） |

还有一处更隐蔽：**`Image.set_pixel` 是截断而不是四舍五入**（`uint8_t(CLAMP(r*255,0,255))`）。
着色算子用的就是 `get_pixel/set_pixel`，所以原生侧必须截断；差这一步，
约 1/4 的字节会差 1，看着像精度问题，其实是取整方式不同。

### 14.4 验证：同一段算子代码跑两遍再比字节

`tests/test_pixel_native.gd` 不另写参考实现，而是把 `FxNativeBridge.set_enabled(false/true)`
各跑一遍**同一个算子**，比对 `get_data()`：

- 逐字节一致：泛光、波纹、变换（三种 wrap）、遮罩（alpha/luma）、五种混合模式、着色；
- 允许 ±1：色相 —— HSV 往返在 float 里做，7844 个字节里约 7 个在
  `int(x*255+0.5)` 的边界上翻一格（0.1%）。**只有这一个算子放宽**，其余放宽就等于掩盖 bug。

GPU 那一侧另有两个探针：`_probe_gpu_ops.gd`（四个 op 是否真的产图）与
`_probe_gpu_diff.gd`（与 CPU 的字节差）—— 实测泛光/波纹**逐字节相同**，色相最大差 1。

### 14.6 构建原生扩展的三道坎（都是环境问题，不是代码问题）

`bash extensions/pixel_native/build.sh template_debug`

1. **SCons 探测不到 Windows SDK**：沙箱把 `reg.exe` 拉黑了，探测只剩 MSVC 的
   include，`<stddef.h>` 全 C1083。解法是给 godot-cpp 的 `SConstruct` 补一段
   `CPPPATH/LIBPATH`（幂等，脚本自动写入）。
2. **响应文件编码**：1089 个对象塞不进命令行，SCons 用**响应文件**；它按 UTF-8 写，
   而 `lib.exe` 按系统代码页读 —— 路径里有中文（`C:\Users\琪诺兔\...`）就全读坏，
   报的却是 LNK1104/LNK1181「无法打开文件 X」，换个文件重试还是同样错。
   **所以凡是进响应文件的路径必须纯 ASCII**：godot-cpp 放 `C:/pw/godot-cpp`，
   静态库输出放 `C:/pw/build/native`。用 GBK 重写同一份响应文件能立刻成功，
   这条是对比实验确认的，不是猜的。
3. **`.gdextension` 跟着产物走**：描述文件在、DLL 不在时引擎每次启动都刷
   「GDExtension dynamic library not found」。所以仓库里放 `.gdextension.in` 模板，
   `build.sh` 在成功构建后生成真正的描述文件（生成物进 `.gitignore`）。

### 14.7 未做

- 泛光/色相/波纹之外的算子还没上 GPU（`image.mask`、`image.transform` 需要读第二张图
  或做坐标重采样，更适合留在原生内核）。
- 原生内核没有 SIMD 指令化（现在是标量 double + 多线程，编译器会做基础向量化）。
- 子图内部的 `image.rays` / `image.shockwave` 仍是 GDScript（示范工程里合计 73 ms，
  是当时最大的一块）。**当时判断「节点专有 → 不该进内核」，第十轮改了口径**，
  理由与做法见 §15.2：进内核的是「径向辐条 / 径向环」这两个**形状图元**，
  不是节点。

# 15. 第十轮：把剩下的脚本算子搬进内核

第九轮结束时示范工程单帧 280 ms，画像里排在最前面的已经不是「某个大算子慢」，
而是**一串 5~50 ms 的逐像素脚本循环**：

| 位置 | 耗时 | 形态 |
| --- | --- | --- |
| `image.outline` | 51.9 ms | 8 邻域 alpha，每像素 8 次采样 |
| 子图 `s_rays` | 36.2 ms | 角度 + 距离场 |
| 子图 `s_shock` | 33.1 ms | 环形距离场 |
| `image.ramp` | 15.7 ms | luma → 三段色带 |
| `image.blur`（精确路径） | 12.8 ms | 可分离盒式 |
| `image.gradient` / `image.shape` / `image.noise` | 各 3~11 ms | 纯 (x,y) 函数 |
| `image.shadow` / `image.invert` / `image.starfield` | 各 2~9 ms | 点运算 / 稀疏光点 |
| `image.pixelfx` 的 `_recolor` | 6.7 ms | 调色板 LUT + 染色 |
| `VfxEngine._composite` / `_post_chromatic` | 5 ms | 合成 / 通道错切 |

它们的共同点：**循环体里没有任何「节点」概念**，只有算术。所以这一轮不新增节点、
不改数据模型，只往内核里加图元。

## 15.1 新增的十六个图元

| 族 | 图元 | 覆盖的算子 |
| --- | --- | --- |

| | `box_blur` | `image.blur` 的精确路径 |
| 点运算 | `levels` | `image.levels`（亮度/对比/伽马，256 项 LUT） |

| | `recolor` | `image.pixelfx` 的调色板/染色/透明度 |
| | `chromatic` | `VfxEngine` 的色差后处理 |

## 15.2 「节点专有」这条线怎么划

第九轮没做 `rays` / `shockwave`，理由是「它们是节点专有的，做成通用图元没有意义」。
这个判断在**函数粒度**上是对的：`rays` 的语义就是 `count/spin/width/length` 那套参数，
搬进内核等于把节点语义复制一份。但把它拆到**几何粒度**就成立了：

- `radial_spokes(size, count, spin, width, length, intensity, center, color)`
  —— 「周期性角度场 × 径向衰减」，本质是极坐标条纹；
- `radial_ring(size, phase, max_radius, width, intensity, center, ring_color, core_color)`
  —— 「以 phase 为半径的环 + 中心核」，本质是极坐标圆环。

两者后续都能被别的节点复用（光晕、雷达扫描、脉冲圈），而且参数表里没有一个是
节点端口名。**判据从「这东西是不是某个节点的实现」换成「换一个节点来调它还说不说得通」。**

## 15.3 精度：第二条位宽边界

第九轮记下的边界是「GDScript 的 double vs `Color` 的 float32」。这一轮踩到第二条，
在**走 `get_pixel` / `set_pixel` 的算子**上：

| 步骤 | 实际位宽 |
| --- | --- |
| `float(buf[i]) / 255.0`（直接读字节） | double |
| `image.get_pixel(x, y).r` | `float(byte) / 255.0f` → **float32** |
| `image.set_pixel(x, y, c)` | `uint8_t(CLAMP(double(c.r) * 255.0, 0, 255))` → 先落 float32 再截断 |

`box_blur` 用的正是 `get_pixel/set_pixel`，第一次逐字节比对时半径 1/3/8 三档全差 1。
原因就是 `norm_byte` 用了 `double(byte)/255.0`。补上 `norm_byte_f32` / `pack_trunc_f32`
之后归零。**判据：看 GDScript 那一侧有没有构造 `Color`。** 构造了就走 float32。

第二条半边界：`_composite` 的光缓冲是 **`PackedInt32Array`**（加性光能叠到 255 以上，
字节存不下），不是 `PackedByteArray`。第一版按字节声明，`--check-only` 当场报
「argument 2 should be PackedByteArray but is PackedInt32Array」。

第三条：`FxMath.h01` 依赖 **int64 环绕 + 算术右移**。C++ 里必须写成
`uint64_t(int64_t(n) >> 13)`；换成 `n >> 13`（无符号右移）图案会整片变样，
而且**不会报错**，只是每次哈希都不同 —— 这类错误只能靠逐字节比对抓。

## 15.5 现在的瓶颈（下一轮的方向）

| 项 | 单帧 | 说明 |
| --- | --- | --- |
| 框架/其它 | ~22 ms | 85 个求值节点，合 0.21 ms/节点 |
| `graph.subgraph` | ~15 ms | 里面只有 ~2 ms 算子 |
| `FxCatalog.ports × 103` | 4.6 ms | `_index_ports` 每帧 `clear()`，端口表全量重建 |
| `_plan_matches()` | 未单独计 | 每帧对 103 个 id 排序 + join + hash |

子图那 15 ms 有明确解释：`_begin()` 里 `ctx.subgraph_runners = {}`，而 **ctx 是每帧
新建的**，所以子图执行器（连同它的结构索引、静态缓存）**每帧重新构造**。
一个 9 节点的子图因此要付 4.7 ms 的首跑价（含建索引 1.8 ms），示范工程正好有两个
子图节点 → 一个子图 × 两次 = 每帧两块首跑价。

这两件事都不属于「替换脚本算子」，留给下一轮，先记在这里：
**要让子图执行器跨帧存活，就得给它一个按（线程, 路径）分区、带互斥的缓存** ——
和第九轮修「静态单例被 6 条预渲染线程互相覆盖」是同一类问题，不能只把
`subgraph_runners` 挪成静态变量了事。

## 15.6 两个 A/B 开关，和「别跨口径比」

| 环境变量 | 作用 | 缺席时 |
| --- | --- | --- |
| `FX_NATIVE=0` | 关掉原生内核，全部回落 GDScript | 默认开（扩展在就开） |
| `FX_GPU=0` | 关掉 GPU compute，全部回落 CPU | 默认开（有设备就开） |

两个开关都只影响「走哪条路」，**不影响语义** —— 这正是 `test_pixel_native.gd` 能拿
它们做逐字节比对的前提。`FX_GPU=0` 还会在 `FxGpuDevice.state_text()` 里如实显示
「被 FX_GPU=0 关掉」，避免把「人为关掉」误读成「设备坏了」。

**口径问题**（这轮踩到的）：同一份工程，开窗 104 ms、无头 63 ms。差的那 40 ms
与 GPU 无关 —— 开窗下 GPU 关 103.7 ms、GPU 开 104.7 ms，两种配置都在 104 左右。
所以是显示服务器与脚本抢主线程。**结论：整帧数字必须标口径，跨口径的对比没有意义。**
第九轮记的 226 ms 是开窗口径，本轮的无头 63 ms 不能直接和它相除；
可比的换算是：无头 259 → 63 ms（4.1×），开窗 226 → 104 ms（2.2×）。
