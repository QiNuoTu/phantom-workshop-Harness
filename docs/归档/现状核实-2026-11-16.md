## 2. 范式符合度（对照 arXiv 2608.25512）

论文的两个维度是：**时间可组合性**＝组件移除后其副作用可完全撤回；**空间可组合性**＝组件能声明并响应式管理组件间依赖。

### 2.1 已对齐的部分

| 论文 | 项目落点 | 判定 |
| --- | --- | --- |
| Def 22 余效果上下文 Σ（键 → 值） | `FxContext.values` / `providers` | 形状对，但**无类型族**（`Dictionary` 任意 Variant） |
| 式 (24) `σ ⊧ d` 依赖满足判定 | `FxContext.satisfies()` | ✅ 一致 |
| Def 26 通知三分类（activating / deactivating / neutral） | `FxFiber.refresh()`：未满足→满足激活；满足→未满足卸载；仍满足但键变 → `on_coeffects` | ✅ **这条做得比文档自己说的还准** |
| Def 8 / Alg 1 带见证的效果函数与逆操作栈 | `FxEffectScope.add(inverse)` + LIFO `dispose()` | 形状对，但只登记「分配类」逆操作（断信号、`queue_free`、恢复旧值） |
| Def 43 组件 = (d, p, e) | `FxComponent.inject / provide / apply` | ✅ |
| Def 44 纤维（含 retire τ） | `FxFiber.active / retired / scope` | ✅ 含 O-Retire 语义 |
| §5.2 声明式装载 + 配置调和 + 热重载 | `FxPluginHost._activation_order()` / `reload_all()` / `plugins.cfg` | ✅ 骨架在 |

### 2.2 三处实质偏离（都会产生可观测后果）

**① 没有值等价关系 `≃ₖ`（Def 24），于是每次写都通知。**
`FxContext.set_value()` 与 `provide()` 都是「写进去 → `notify([key])`」，从不比较新旧值：

```gdscript
func provide(fiber, key, value) -> void:
	values[key] = value          # 旧值直接丢弃
	providers[key] = fiber.uid
	notify([key])                # 值没变也通知
```

后果：这正是 #1 的**语义层根源**。下游所有「响应式重建」都建立在这条通知上，通知过频 → 重建过频。论文的 `≃ₖ` 要求「只有观测上不等价才算变化」，项目里没有这个概念。

**② `set` 缺前置条件 `k ∉ dom(σ)`（Def 23），实际是 last-wins。**
`provide()` 不检查键是否已被占用；`FxRegistry.ops[key] = value` 也是后登记覆盖先登记。
论文 §4.2 明确要求「同一 registry 里两个 fiber 的供给不得相交」。项目把「覆盖」当成有意特性（`render.gpu` 覆盖 `image.blur` 就是这么做的）。
判定：**不是 bug，但要写进文档**——它使「空间可组合性」的互斥保证不成立。

**③ 没有 isolation / interception / 派生上下文（Def 27、30–32）。**
`FxContext` 是一张平表，没有 realm，没有 `intercept`，没有子上下文；`FxFiber` 有 `parent` 字段但从不派生 `ctx`。
后果：无法给两个组件绑定同一键的不同值，也无法在依赖访问路径上插入横切逻辑（日志、缓存、mock）。这是「一切皆插件」在**测试替身**场景下的硬缺口。

### 2.3 时间可组合性只在一个方向成立

`FxEffectScope` 保证「组件自己做的事能撤回」。但**图与算子层不在 scope 里**：
`FxPluginHost.shutdown()` 先调 `FxGraphFacade.access().reset_runtime_tables()` 整体清表，再回放逆操作——
这是「先销毁再恢复」的兜底，不是「逆操作恰好恢复原状」。

判定：**UI/服务层的时间可组合性成立，图/算子层不成立**。文档不能再写「完全可撤回」。

> 一句话：这份代码是**范式指导下的工程实现**，不是范式的等价实现。README 目前写的是「借鉴边界」，这个口径是对的，别改回去。

## 3. 六点逐条核实

### 3.1 #1 只有数据改变才触发重建

**实测**：`core.render/fx_render_service.gd::_on_store_changed()` 有三道闸门。

| 闸门 | 条件 | 行为 |
| --- | --- | --- |
| 布局键 | `_is_layout_only(keys)`：`positions` / `size` / `doc` | 直接 return，不换桶不重画 |
| 内容身份 | `_doc_revision()` 未变且不含 `tracks`/`time` | return（`selection` 只刷新预览范围） |
| 分档失效 | 按 keys 分派 `invalidate(kind)` | `content` / `derived` / `display` 三档 |

**证据**：`test_editor_ui` 的「拖动节点不改变缓存指纹（不换桶）」这条**每次都过**；失败的是另外两条（`ready` 1→2、渲染 1 次）。

**归因**：**不是触发点太多，是失效粒度太粗。**
`FxGraphRunner.invalidate_cache()` 只有一种行为 —— `_static_cache.clear()` 全清。改一个节点的 `radius`，整桶 60 帧与全部节点的跨帧静态表一起作废。IR 计划层（`core.compile`）已经能算出「受影响子集」，但**没有接口把它交给缓存**。

**修法（纯插件）**：
1. `core.graph` 的静态缓存键从「结构签名」改为「(结构签名, node_id 及其上游闭包指纹)」，让作废能按节点记账；
2. `core.render` 在 `_on_store_changed` 里用 `compile_plan` 求「改的这几个节点的下游闭包 ∩ live」，只作废这些；
3. 桶不重建，只把受影响帧标记为「待重算」——绿格变黄格而不是清空。

**顺带修一个测量工具**：`test_editor_ui` 那两条断言会被**后台预渲染**污染（6 帧窗口里预渲染归档了一帧 → `ready` +1、`rendered` +1）。同一套件连续跑两次：一次 234/0 通过，一次 232/2 失败。修法是断言前 `prefetcher.cancel()` 或断言窗口内忽略非播放头帧的归档。**这是测试隔离问题，不是产品缺陷**，不要为了让它变绿去改失效逻辑。

### 3.2 #2 两条预览管线

**实测**（`diag.cache` 的「两条预览管线」一节）：

```
节点小图：边长 128 · 算子质量 0.50 · 刷新 1.50s
输出预览：恒精确帧（降采样：关，内核钉死）
```

| 通道 | 现状 | 问题 |
| --- | --- | --- |
| 节点小图 | `preview_limit/preview_operator/preview_refresh_ms` 可调 | 但小图是在**已算完的全分辨率图**上 `duplicate()+resize()`，省的是像素拷贝不是求值 |
| 输出预览 | 恒全精度 | 与导出同精度，交互期白付 |
| 添加节点样张 | `FxNodePreview`（独立 `quality=0` 求值器） | 唯一真正的低质量管线，但只服务样张 |

**归因**：`core.render` + `editor.preview`（插件）。挡路的是内核不变量：
`scripts/graph/kernel/fx_quality_policy.gd:47` 把 `output_downscale` 钉死 `false`，注释写的是「输出链永不降采样」——但实现成了「**任何**显示通道都不许降采样」。

**修法**：把不变量精确成「**归档/导出**不降采样」，另开 `display_scale` / `display_quality` 两个键。显示路径按 `display_scale` 降采样 + `display_quality` 降算子档，缓存/导出仍全精度。这需要改内核一行语义 + 注释（**Q3**，唯一一处必须动内核的地方）。

**已知收益口径**（上一轮实测，别夸大）：示范工程 192×108 抓小图 +0.3%、算子 1.0→0.5 +3.2%；512² −1.5%/−1.1%。**成本不在缩放，在「重算 8 个预览根 0.53s」。** 所以 #2 的真正收益要等「预览根独立求值」做完才出现，单独改质量档位几乎无感 —— 这条必须写进文档，否则又是一次「说了做不到」。

### 3.3 #3 运行时剪枝

**实测**：`core.compile` 已产出纯数据计划，示范工程 **Live 85 / Dead 18**（结构剪枝上界 17.5%）、常量折叠 2；`_profile_frame` 实测求值节点 85，与计划自洽。

**仍缺的（按收益排序）**：

| 缺口 | 现状 | 谁的问题 |
| --- | --- | --- |
| 执行流修剪 | `_exec_entries()` 把所有「无 exec 入边」节点当入口，与输出链无关 | `core.graph` |
| `evaluate_always` 旁支全跑 | `run()` 末尾线性扫全图补跑 | `core.graph` |
| 无关键帧仍按时间相关 | `_build_time_dependence()` 里 `has_exec_in` 即判 true | `core.graph` |
| 端口表每帧重建 | `_index_ports.clear()`，77 类型 × 103 节点 | `core.graph` |
| 子图 runner 每帧新建 | `ctx.subgraph_runners` 随 ctx 新建 → 2 次调用付 14.1ms | `core.graph` |

**注意口径**：Dead 剪枝是**上界不是提速**（拉取式求值本来就跳过 Dead）。真实收益来自「常量折叠的 steps 3→2」「汇点 O(N)→O(|sinks|)」与可观测性。不要把它写成「提速 17.5%」——上一轮已经踩过这个坑。

### 3.4 #4 管线完全 GDExtension

**实测**（`_profile_frame`，示范工程，2026-11-16）：

```
整帧 77.08 ms · steps=104 · 求值节点 85
算子累计 55.46 ms（72.0%）· 调用 97 次 · 平均 0.57 ms/次
框架/其它 21.62 ms（28.0%）
累计前 5：graph.subgraph 14.12 · image.recipe 4.70 · image.bloom 3.75 · output.final 3.56 · image.wave 1.73
```

**现状**：原生内核 25 个图元、20 处算子调用点，覆盖 77 个算子里的 32%；**求值主循环、参数解析、端口转换、Image 分配全在 GDScript**——那就是那 28%。

**判定**：**不满足，且这是本项目最大的一笔未开工工程量。** 分三步走（每步都可独立验收）：

| 阶段 | 内容 | 预期 | 风险 |
| --- | --- | --- | --- |
| S1 | 求值主循环下沉（拓扑遍历 + 参数解析 + 端口转换 + 池化 Image） | 28% → 10% 以内 | 中：要与 GDScript 路径逐字节对拍 |
| S2 | 剩余重算子下沉（recipe / bloom / final / transform） | 72% 中约 40% 再削一半 | 低：已有 25 个图元的成熟模式 |
| S3 | 编译器后端（IR → WGSL / compute pass） | 与画布尺寸脱钩 | 高：要两条路径结果一致 |

**纪律**：任何一步都不能让「GDScript 参考实现」消失 —— 现在的 `tests/test_pixel_native.gd` 就是靠 `set_enabled(false/true)` 两跑对拍守住精度的，这条路子要保留。

### 3.5 #5 GDExtension 不是插件

**实测**：`plugins/pixels.native/` 目录里只有 `src/`（拆分源码）与空的 `native/`，**没有 `plugin.json`、没有 `plugin.gd`**。插件宿主扫描内置根时把它当插件目录，报：

```
✗ [插件加载] 跳过 res://plugins/pixels.native：缺少 plugin.json / plugin.gd
── 汇总 ──
错误 2 · 警告 0 · 信息 0 ｜ 需要动手：内核 1 / 插件 1 / 装配 0
```

**这一条本身就是 #7 的活教材**：错误文本里没有插件痕迹，归因规则「没有插件痕迹 → 内核」就把它判给了内核。**规则本身有缺陷**，不是内核有问题。

**修法（两条路，见 Q1）**：
- **A（快）**：把 `plugins/pixels.native/src/` 移到 `extensions/pixel_native/src/`，仓库里只剩一处原生源码，插件根恢复干净。原生仍是「扩展」不是「插件」。
- **B（对）**：把 `plugins/pixels.native/` 做成真插件：`plugin.json`（id / version / contract / provide `pixels.native`）+ `plugin.gd`（`capabilities()["pixels.native"]` 暴露可用性与绑定数）+ 自带 `.gdextension`。`core.pixels` 只通过契约取，缺席回落 —— 与现在 `FxNativeBridge` 的回落逻辑一致，只是把「桥」升级成「插件」。

推荐 B，但它必须与 #6 一起做（否则插件壳里放一个 1635 行单体文件，等于没拆分）。

### 3.6 #6 单体 CPP

**实测**：

| 位置 | 行数 | 类 | 绑定 | 是否被构建 |
| --- | --- | --- | --- | --- |
| `extensions/pixel_native/src/fx_pixel_native.cpp` | **1635** | `FxPixelNative` ×1 | 28 | ✅ `SConstruct` 的 `Glob("src/*.cpp")` |

1. 立刻：按脚本输出逐条改，改完脚本必须返回 0；

| plugin | 41 份 `plugin.json` | 全 `0.1.0` + `contract ">=0.1.0 <0.2.0"` | ✅ 一致，无需集体改 |
| project_format | `version.json` → `project_format`；`HOST_VERSION` | `0.1`（`SUPPORTED=["0.1","1.0"]`） | ✅ |

`v0.1.0` 是历史 tag，README 已声明「可发布」撤回。**不建议删 tag**（改写历史的风险大于收益），建议加一条注释 tag 或在 tag message 里补「已撤回」。

### 5.2 建议方案

用户要求「不能是 1.0.0、是最初测试版」—— `0.x.y-alpha` 这个形态本身是对的，**问题是没执行到位**。

| 号 | 建议 | 理由 |
| --- | --- | --- |
| app | 本轮 `0.0.11-alpha` | 纯文档/工具/结构修，不算功能增量 |
| kernel | 保持 `0.1.2`；若采纳 Q3（`output_downscale` 语义）→ `0.1.3` | 语义收窄属于 patch（现有插件不改代码仍能跑） |
| plugin | 只涨动过的：`core.render` `0.1.1`、`core.graph` `0.1.1`、`pixels.native` `0.1.0`（新建） | 改一个插件不该让 41 个集体 +1 |
| format | `0.1` | 文件格式没动 |

并补两条硬规则进 `docs/版本策略.md`：
1. **涨 app 必须同时过 `check_docs.py`**（否则版本号又会在文档里分裂）；
2. **新插件首次出现即 `0.1.0`**，禁止 `1.0`；`1.0` 只在「契约连续两个 minor 无破坏性改动 + 有第三方插件」时出现。

## 6. 调试工具：分清「插件问题 / 内核问题」

### 6.1 现有能力（不重复造）

| 工具 | 回答 | 归属 |
| --- | --- | --- |
| `--fx-diagnose` | 有什么（插件/节点/面板/设置/语言包/缓存位置） | 基座启动步骤 |
| `diag.blame` | 谁的错（内核 / 插件 / 装配） | `editor.diagnostics` 插件 |
| `diag.cache` | 谁在重建、哪一档、清了几格 | 同上 |
| `diag.compile` | 图编译成什么（拓扑/类型/常量/Live/帧段） | `core.compile` 插件 |

四件都是插件，停用即消失 —— 这个设计是对的，别改成基座内置。

### 6.2 三个真实缺陷（本轮实跑暴露）

**T1 归因靠「错误文本里有没有插件痕迹」猜。**
`plugins/pixels.native` 缺 `plugin.json` 这条，文本里没有插件 id，于是被判给内核。可它发生在「插件扫描」这一步，属于**装配**。
修法：`FxBoot.error()` 与 `_add_host_error()` 带上 `step` 与 `scope` 字段（`scope ∈ {kernel, assembly, plugin:<id>}`），`diag.blame` 直接读字段，不再猜文本。**这是基座 20 行的改动**，但它是「诊断工具」的核心，值得破例（见 Q5）。

**T2 `diag.compile` 只能看启动示例文档。**
现在跑出来是「节点 6 · Live 6 / Dead 0」，因为启动示例只有 6 个节点。要看书里那份 103 节点的示范工程，没有任何入口。
修法：支持 `--fx-arg=<path.fxproj>`，解包后编译并打印（只读，不改工程）。

**T3 `diag.cache` 在无头下永远 0 条采样。**
它靠运行时事件，无头没有交互，于是永远是「没有记录到任何重建」。这是一个**只能开窗用**的工具 —— 而验收时需要的是可复算。
修法：加 `--fx-arg=script:<json>`，用一段声明式操作序列回放（改参数 / 拖节点 / 切档位 / 播放 2 秒），无头也能产出事件流。

### 6.3 建议新增两项

| 工具 | 回答什么 | 为什么需要 |
| --- | --- | --- |
| `diag.abi` | 原生扩展在不在、绑定几个类/方法、GDScript 与原生逐算子是否逐字节一致 | #4/#5 之后，「快」与「对」必须一起报；现在只能靠跑整套测试 |
| `diag.deps` | 停掉插件 X 谁会坏（贡献 → 消费者反向索引） | 「删任一插件仍能启动」这条闸门现在是手工试 |
