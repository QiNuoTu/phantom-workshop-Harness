### 2.4 「GPU 渲染服务器」名不副实（P1）

`plugins/render.gpu/fx_gpu_backend.gd:39-49`：`frame()` 的实现是

```gdscript
var result := _cpu.frame(doc, t, policy, runner, ctx)
```

即 **GPU 后端的主求值路径就是 CPU**。GPU compute 只出现在 `postprocess()`（发布前的主线程锐化）
与 `FxGpuOps`（blur / mix / outline，且工作线程里自动回落 CPU）。

## 3. 你提出的四点：现状与根因

### 3.1 「只有数据改变才触发缓存重建」—— **本轮已做失效分档（见 §5.5）**

**不是「到处触发」，是「一触发就全清」。**

判据其实已经有了：`FxRenderService._on_store_changed()` 里有「内容身份没变就什么都不做」的闸门
（`fx_render_service.gd:1102-1110`）。但 `invalidate()` 绕过了它：

| 触发点 | 代码 | 实际清掉的东西 |
| --- | --- | --- |
| 任何 `applies=runtime` 的设置变化 | `fx_shell.gd:257-259` | 静态缓存 + 样张缓存 + 显示缓存 + 世代 + 重画 |
| 播放 / 暂停 | `fx_render_service.gd:581` 附近 | 执行器静态缓存（本来就按 `doc_signature` 键控） |
| 改结构 / 参数 / 轨道 | `fx_render_service.gd:1144-1148` | 执行器缓存 **+ `FxRenderBroker.invalidate()`**（销毁后端实例、重置 GPU composer） |
| 后端切换 | `fx_render_api.gd:29-34` | 同上（这一处是合理的） |

最刺眼的一条：**`general.locale`（界面语言）被算作 `applies=runtime`**。
（复核更正：`plugins/core.i18n/fx_i18n_api.gd` 里实际写的是 `"ui"`，它会走 `rebuild_ui` 分支、
**没有**进渲染失效。所以「换语言作废整段缓存」这句当时说过头了。
真正的粗粒度来源是另外 22 个 `applies=runtime` 项：线程数、缓存上限、算子系数、后端……
它们全部走同一个 `invalidate()`。）

`invalidate()` 一个函数干了四件事（`fx_render_service.gd:610-616`）：

```gdscript
runner.invalidate_cache()      # 跨帧静态缓存
FxNodePreview.clear_cache()    # 「添加节点」面板里所有样张
_cache_dirty = true            # 帧缓存桶
_epoch += 1                    # 所有在途结果作废
request_render()
```

**归因**：`core.render` 插件 + 外壳里那一行**无条件调用**。后者是基座写死的决策，
插件侧无法绕开，所以本轮在基座只加了一个「转达」而不加领域判断。**已完成**，见 §5.5。
正确形态是：`invalidate()` 收成「按内容身份做差量失效」，并拆成
`invalidate_static / invalidate_bucket / invalidate_display / invalidate_all` 四档，
由调用方声明自己改的是什么；设置项则区分「影响画面」与「只影响界面」。

### 3.2 「节点预览小窗 + 输出预览应走独立可调质量管线」

现状：三条消费路径（输出预览 / 节点卡片小图 / 添加节点样张）共用**一条主求值**，只有第三条例外。

- 输出预览：`FxPreviewPanel` 只订阅 `rendered`，收到的是**全分辨率、与导出同精度**的图。
- 节点小图：`FxGraphRunner._capture_preview()` 在**已经算完的全分辨率图**上 `duplicate()` + `resize()`，
  运算成本**已经付过**；`preview_limit` 只决定缩放上限，不省计算。
- 播放时：为了拿到小图，`start_preview_pass()` 会把整张图**再跑一遍**。
- 唯一现成的低质量管线是 `FxNodePreview`（`_runner.quality = 0`），但它只服务「添加节点」面板。

硬约束挡在这里：`scripts/graph/kernel/fx_quality_policy.gd:24,47`

```gdscript
"output_downscale": false,   # 硬约束：插件不能覆盖
```

「输出链永不降采样」原本是为了保证**缓存帧 = 导出帧**，这是对的；
但它被实现成了「**任何**显示通道都不能降采样」，于是交互预览也只能吃全精度。

**归因**：`core.render` + `editor.preview` 插件。需要一个**显示管线**概念：
`display_scale` / `display_quality` 两个新策略键（不碰 `output_downscale` 的不变量），
显示走降采样+低算子质量，缓存/导出仍走全精度。属于**插件问题**，
但需要内核确认「`output_downscale` 只约束归档路径」这一语义——见 Q3。

### 3.3 「运行时没有剪枝，无用节点和无关键帧节点不该参与运算」—— **第四轮已做 IR 层（§5.6）**

**部分不成立，缺的部分是真的。**

已有的：求值是拉取式（`_eval` 从 `output` 反向拉），**不可达节点天然不求值**。
这在 103 节点工程里是有效的。

缺的（都是真的）：

1. **`evaluate_always` 旁支无条件跑**：`run()` 末尾遍历全部节点，
   `evaluate_always=true` 的一律补跑——包括没接进输出链的 IO 节点（`godot.export/nodes_io.json` 5 个）、
   输出预览口、子图节点。
2. **执行流入口全跑**：`_exec_entries()` 把所有「没有入边 exec」的节点当入口，与输出链是否可达无关。
3. **无关键帧也按时间相关处理**：`_build_time_dependence()` 里
   `if def.has_exec_in: dependent = true`——所有执行流节点及其**全部下游**永远进不了静态缓存，
   哪怕整条链一个关键帧都没有。
4. **单元关键帧轨道也按时间相关**：`FxTracks.collect()` 只看「有没有 track」，不看「轨道是不是常量」。
5. **没有帧区间分析**：轨道在 `[f, f+k]` 上取值不变的段，仍逐帧重算。
6. 每帧 `_index_ports.clear()` 重建端口表，`_resolve_params()` 每节点深拷贝默认参数。

**归因**：`core.graph`（执行器）为主，`core.render`（预览需求）为辅。属于**插件问题**。

**第四轮进展**：新增 `core.compile` IR 插件（DAG / 类型检查 / 常量折叠 / Live 判活），
上面第 1 条改成「有计划时按拓扑序遍历 sinks，不再全图线性扫描」，但**汇点仍然全部求值**
（6 个导出节点有写文件副作用，不能剪）；第 2 条执行流节点被显式列为根，也仍全部求值。
第 3–5 条已由**第五轮的帧指纹分段**（§5.7）绕开：`_build_time_dependence()` 判定保留原样，
跨帧缓存改由「签名 + 帧指纹」共同决定，常量/step 轨道不再逐帧重算。
第 6 条（端口表每帧重建）与执行流修剪**仍未做**。

### 3.4 「渲染可落到 SubViewport + Shader，目前还有高压算子」

现状：

- `SubViewport` 只用于 `core.shader` 的 `.gdshader` 节点（`fx_shader_runtime.gd`），**不是通用渲染通道**。
- 精确模糊是 GDScript 逐像素读改写（`core.image/fx_ops_image.gd:_box_blur`），
  192×108、r=32 即 20 736 像素 × 4 通道 × 两遍。
- 工作线程里 GPU 算子自动回落 CPU（这是对的，避免跨线程碰 RD），
  于是**预渲染**这条最需要算力的路径 100% 是 CPU。
- 整帧 480–530 ms 的来源就在这里。

**归因**：`render.gpu`（缺口）+ 新增编译/后端插件。

## 4. 关于 IR 建议：落点在哪里

你给的链路（IR → DAG → 类型检查 → 常量折叠 → 死节点剔除 → VM / GPU 管线）与现状的差距：

| 环节 | 现状 | 差距 |
| --- | --- | --- |
| 类型检查 | 运行时 `FxPortType.cast_value` 逐边转换 | 没有静态检查，类型错误要等跑到才炸 |
| 常量折叠 | 无 | 参数全常量的子树每帧重算 |
| 死节点剔除 | 仅靠拉取式求值 | 旁支 / 执行流入口 / 预览需求未纳入 |
| 中间表示 | 无，直接走 `node → op Callable` | 每帧重复：索引、参数解析、Callable 分派 |
| 实时预览 | GDScript 解释 | 无字节码/VM |
| 最终渲染 | CPU 逐像素 + 少量 compute | 无 GPU pass 列表 |

**建议的落点（全部是插件，不动基座）**：

1. 新增 `core.compile` 插件：消费 `graph.facade`，产出 `FxProgram`（指令序列 + 端口类型表 + 死节点集合 + 常量表）。
   图语义仍在 `core.graph`，编译层只读不写。
2. `core.graph` 增加 `FxGraphRunner.compile()` 入口（同插件内演进），执行器优先跑已编译程序，
   没有编译结果时退回现有解释路径——**两条路径必须同结果**，用现有 77 算子回归守住。
3. 新增 `render.shader` 后端（实现 `FxRenderBackend`）：把 `FxProgram` 翻译成 SubViewport + 全屏 shader pass 列表。
   导出与缓存走它，预览仍走 CPU 轻量路径。
4. GDExtension 留作最后手段：`native_ops()` 契约已经存在（`fx_plugin.gd:70`），
   把最贵的 2–3 个算子（精确模糊、distort 重映射、颜色 LUT）先落成原生，
   比整体重写便宜得多。

**顺序建议**：先「剪枝 + 分段」（3.3）→ 再「显示管线」（3.2）→ 再「IR/VM」（4.1-4.3）→ 最后 GPU 后端。
理由：前两步是**删工作量**，后两步是**换实现**；先删掉不该算的，再谈怎么算得快。

```
── 判定 ──
! 1 次重建只动了 meta 段
· 14 次重建确实改了图/连线
· 最频繁的重建来源：改参数（11 次）
```

**结论要改写**：之前「桶被反复重建抹掉绿格 = 数据没变也在重建」这个推断**不成立**。
实测里 14/18 次分段哈希确实变了（图 / 连线），是测试序列自己在 11 秒内连续改参数、
撤销、改时间轴、换工程造成的**必要重建**；8 次通知被「内容身份没变」闸门挡下，
说明闸门是有效的。真正可疑的只有：

1. **1 次只动 meta 段**的重建（时间轴 2.0s → 0.2s，帧数 60 → 6）；
2. **末尾两条同一毫秒、同一指纹对**的背靠背重建（`1371178710_30_200 → 750171025_30_200`），
   且前后出现 `fp_before` 为空、`帧 0→6` 的记录 —— 指向 `cache.configure()` 在
   `render.cache_location` 变化时把 `_fingerprint` 清空，而不是「数据没变也重建」。

所以这条断言的失败归属是：**测试序列把 18 次真实内容改动压缩在几秒内，
末尾再叠一次缓存根切换，等待窗口（12 × 0.2s）内的绿格被最后一次重建抹掉**。
不是缓存实现乱重建，也不是内核问题。下一步要么让测试在断言前等文档稳定，
要么把 `configure()` 的换根与「内容指纹」分开记 —— 两个都属插件侧，不动内核。

### 5.4 一个存量缺陷：那条「标绿」断言在 HEAD 上也间歇失败

> **已于第六轮收口**，见 §5.8。当时的推断「与『数据没变也重建』同源」是错的：
> 真正原因是**换桶之后没人补算当前帧**。以下保留当时的取证过程。

**现象**：全量跑时 `test_editor_ui` 的「刚渲染过的当前帧标绿」间歇失败，单独跑该套件却全过。

**先确认责任归属**（不背不该背的锅）：

| 对象 | 跑法 | 结果 |
| --- | --- | --- |
| 干净基线（`git worktree` 拉 HEAD） | 全量，2 次 | **2/2 失败**在同一断言 |
| 本树（本轮改动） | 全量 | 也出现过失败，也出现过通过 |
| 两者 | 单独跑该套件 | 多次全过 |

结论：**存量时序缺陷，与本轮边界修复无关**。中途一度以为「改版本号」是原因，
那是典型的时序假象（改动改变了加载耗时），不是因果。

**埋点看到的事实**（计数器，不打印，避免扰动时序）：

```
arch=8  exact=5  pending=3  prepares=24  gate_blocked=0
```

- `arch=8`：归档确实发生了 8 次，其中 5 次是精确帧（绿）；
- `gate_blocked=0`：稳定期闸门**一次都没挡**——所以问题不在闸门（据此回退了试验性放宽）；
- `prepares=24`：整轮里帧缓存桶被**重建了 24 次**；每次重建都会把 `_states` 清空。

**推断**：断言失败不是「没算出来」，而是「算出来变绿之后，桶在等待窗口内又被重建，
绿格被抹掉」。而桶重建的唯一原因是**内容身份变化**——也就是你说的第 1 条：
「数据没变也在重建」。两者同源。

**我没做什么**：没有改这条断言，也没有提交未验证的行为改动
（试过把闸门判据从 `_cache_dirty` 改成指纹比对，埋点显示 `blocked=0`，证明不是它，已回退）。

**建议**：把「重建归因」做成工具（`diag.cache`）：每次 `prepare()` 记录
「谁触发、哪些键、指纹 X → Y、抹掉几格」，先让这件事变成可查的事实，再谈减少重建。

**必须说清的一点**：17.5% 是「理论上可以不参与」的上界，**不是实测提速**。
拉取式求值本来就跳过了 Dead 节点，所以结构剪枝在这个执行器里收益天然有限；
本轮真实收益是常量折叠（`steps 3 → 2`）、汇点遍历从 O(N) 降到 O(|sinks|)，

**判活公式的两处精确化**（实现时发现，不是放宽标准）：原式 `∪{evaluate_always}`

因此改成 `∪ ⋃Reachable(s) ∪ ⋃Reachable(e)`。理由见 `docs/剪枝与预览根集合.md §4`。

## 5.8 「标绿」断言收口（第六轮，§5.4 的结论）

§5.4 当时只把责任判到了「桶在等待窗口内被重建」，没找到**为什么**。这一轮把归因做细后收口了。

**新证据**（`diag.cache` 的逐节点明细，本轮新增）：

```
t=9.64s  归档时补桶  2273364494_30_2000→1333485966_30_200  帧 60→6   变化：meta
t=10.80s 归档时补桶  →3419825533_30_200                     帧 0→6    （无分段信息）
t=11.02s 0.25s 巡检  1333485966_30_200→3419825533_30_200    帧 6→6  清 5 格  变化：图
      变了：节点+subgraph_1
```

**结论**：绿格不是「算错了」也不是「没算完」，是**算完变绿之后文档又变了一次**
（`subgraph_1` 被加进来，这是上一个用例关标签时把打包结果写回主干），
换桶把绿格清掉，而**换桶之后没有任何人重新算当前帧**——于是等到超时也是灰的。

**改动**（全在插件层，内核零改动）：

| 项 | 内容 |
| --- | --- |
| 换桶补算 | `_refill_after_rebuild` 一次性标志，`_tick_cache` 里补算当前帧一次（见 `docs/诊断与归因.md §7.6`） |
| 指纹补齐 | `content_of()` 抹掉 `collapsed` 与 `frames[].rect`：折叠卡片、挪分组框不再让整段缓存作废 |
| 归因细化 | `detail_of(doc)` + 桶事件带 `detail_before/after` → `diag.cache` 打出 `变了：节点~blur` |
| 静默写入 | 指纹变了、修订号没变 → 判 `error`：有人绕过 `mutate()/attach()` 直接改文档字典 |

**实测**：单跑 `test_editor_ui` **12/12 通过**（修复前约 2–3 次挂 1 次）；
全量 **17 套 / 1088 断言 / 0 失败**；`diag.blame` 内核 0 条。

**顺带澄清一个先前的推断**：§5.4 曾把「24 次重建」与「数据没变也重建」归为同源。
细分段哈希显示 18 次里 14 次是**真内容变化**——那部分重建是必要的，
该修的是「换桶后的补算」而不是「让定桶更懒」。
