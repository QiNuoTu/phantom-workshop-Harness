## 4. #4 / Q2 的拆分（为什么不是一次做完）

「主循环进 C++」不是一个补丁，是把 900 行 GDScript 求值器换一种语言重写；
真正贵的不是翻译，而是**语义漂移**（子图、执行流、分辨率档、预览捕获、缓存分档）。
所以切成四步，每步都能单独对拍、单独回滚：

| 步 | 内容 | 验收 |
| --- | --- | --- |
| S0 | **先删工作量**：子图执行器复用、端口表跨帧缓存、差量失效 | 已完成：整帧 84.4 → 68.7 ms |
| S1 | 把「一步」抽成纯数据：`{op_id, params, inputs, out_id, scale}`，用 `env` 字典传上下文；GDScript 侧只负责构造这一步 | 抽完后 GDScript 与 C++ 两条路径能对同一份 step 列表逐字节一致 |
| S2 | C++ 侧 `fx_exec_steps(steps, env) -> images`：只做调度与缓冲，算子仍回调用 GDScript Callable | 调度开销成为可测的一行；决定「哪些算子在 C++ 里直接做」 |
| S3 | 逐族把算子搬进 C++（先 `output.final` / `image.transform` / `image.wave` 这类纯像素的），GDScript 版保留为对照实现 | 每族都要有「关掉原生仍逐字节相同」的对拍断言 |

S2 之前**不要**动 `fx_graph_runner.gd` 的语义分支：现在每一处分支都有测试锚着，
重写时才不会「顺手改了个看起来更合理的行为」。

## 5.5 开窗才炸的那一类问题（新增检查）

`test_*` 全在 `--headless` 下跑，那里不执行 `_draw()`、不建纹理、预渲染线程常被跳过。
于是「多条预渲染线程共用一个有状态的引擎实例」这类问题一路活到真机：

```
SCRIPT ERROR: Out of bounds get index '19320' (on base: 'PackedInt32Array')
   at: VfxEngine._add (plugins/core.recipe/vfx_engine.gd)
```

真因不是索引算错，而是 `VfxEngine.configure()` **先写 `_w/_h`、隔 70 行才 resize 缓冲**；
这段时间里另一条预渲染线程进来渲染，`_in_bounds` 用的是新尺寸、缓冲还是旧的（甚至空的）。
修法两手：`configure()` 与 `render()` 互斥（引擎实例按节点缓存，天生共享）、
尺寸与缓冲一次性换。顺手把 `render` 尺寸并入配方缓存签名（配方没写 width/height 时它跟随画布）。

由此新增 **运行时冒烟** `bash tools/smoke.sh`（开窗，约 30 s）：
打开示范工程 → 逐节点改参 → 显示倍率 → 播放 → 导出 → 存盘读回，
并把**引擎级报错**也算失败（`SCRIPT ERROR` / `Out of bounds` / `Invalid access`）。
headless 套件全绿不再等于「能跑」。

## 5.6 第二个开窗才炸的问题：运行期停用插件会死锁

主线程在 `set_enabled()` 里 `lock()` 等渲染闸门，而工作线程正持着那把锁求一帧，
那一帧的 GPU 算子又要靠**主线程泵**推进 —— 主线程一堵，泵就停，锁永远不回来。
真机表现是「点停用插件，界面卡死」。

改法：主线程一律不阻塞等这把锁。

| 入口 | 以前 | 现在 |
| --- | --- | --- |
| `FxPluginHost.set_enabled()` | `lock()` 阻塞 | `try_lock`，失败排队，下一帧 `tick()` 重试（渲染服务每帧先泵再试） |
| `FxPluginHost.shutdown()` | `lock()` 阻塞 | 「等一会儿 → 泵一次 → 再试」，2 s 上限，超时走无锁路径并告警 |

冒烟里连「停用 → 启用 → 断言桥真的回落/恢复 → 断言无残留排队」一起验。

## 5.7 第三个开窗才炸的问题：缓存帧不记「自己是哪份文档算的」

用户报的是「改参数没效果、预览不回来」，复现出来是三张互不相同的图：

| 取法 | 平均色 |
| --- | --- |
| 导出帧 0（项目定义的真值） | (61,42,104) |
| 缓存里「绿色就绪」的帧 0 | (132,121,161) |
| 屏幕上那一张 | (89,76,129) |

根因不是求值，是**分发**：桶按内容指纹重建，但指纹是合成哈希，而预渲染线程与
主线程并发写 —— 第 N 版文档算的帧能活到第 N+1 版，还带着「精确就绪」的绿标。

修法：帧自带 `identity`（算它那一刻的 `content_key`），分发前 `accepts()` 校验；
播放供帧、停播定格、暂停态贴帧三处都要过这一关。磁盘恢复的帧身份为 `-1`
（桶目录即指纹），放行。

同一轮顺带修掉三处静默丢帧：过期结果丢弃后不重算（脏位没放回）、`stats["paused"]`
泄漏到后续每一帧（播放命中被算成定格帧）、定格帧被贴两次。

门禁补强（都是这一轮才有的）：

| 检查 | 内容 |
| --- | --- |
| `smoke` 不变量 | 导出首帧 == 缓存首帧；缓存首帧身份 == 当前文档 |
| `smoke` 可见性 | 改字号后**整图逐字节**必有差异（不是采样点） |
| `FX_TRACE_NODE` | 按节点打印缓存判定，回答「为什么这帧没重算」 |

## 6. 本轮顺手修掉的一个真 bug（写在这里，防止被当成「测试抖动」）

`test_editor_ui` 的「播放推进时间 0.000 → 0.000」长期被当成偶发。它不是抖动：
播放急件在**换文档稳定期**被 `_archive_result` 拒收后，`_urgent_submitted` 仍停在那一帧，
于是后续的重新提交被 `next != _urgent_submitted` 永久挡掉 —— 播放会一直卡到
`STALL_LIMIT`（0.35 s）强制放行。机器越快、每帧 delta 越小，这个卡顿越容易触发。
修法：结果回来就清 `_urgent_submitted`（哪怕被拒收），下一帧自然会重提。
